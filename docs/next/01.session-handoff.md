## 3. 다음 작업 옵션 (사용자 선택 대기)

### 옵션 A. `kiwi-planner` (권장)

**왜:** speckiwi MCP 의 Phase>Task 구조로 plan.md + 사이드카 JSON 양면 SSOT 생성. plan-step ↔ REQ trace link 자동 영속화 (`add_trace_link` MCP 호출). 본 SRS 가 이미 speckiwi 호환이므로 자연 연계.

**입력:** 현 active target `v1.0.0` 자동 사용.

**산출물:** `docs/plan/plan-v1.0.0.md` + 사이드카 JSON.

**호출 예시:**
```
/kiwi-planner
```
또는 args 로 target 명시:
```
/kiwi-planner target=v1.0.0
```

### 옵션 B. `snoworca-planner`

**왜:** plan-contract-v1 형식. snoworca-coder 직접 입력 가능. Phase 별 구현 계획 + acceptance_tests 구조화 (shell/cmd/expected_exit/stdout_regex). source_anchors path:line-range 의무.

**입력:** SRS 5개 파일 + 80.decisions.md + 연구 문서.

**산출물:** `docs/plan/...` (plan-contract-v1.1 형식).

**호출 예시:**
```
/snoworca-planner SRS_PATH=docs/spec/ DECISIONS_PATH=docs/research/80.decisions.md
```

### 옵션 C. `snoworca-feasibility` (planner 진입 전 검증)

**왜:** REQ별 구현 난이도 (Low~Infeasible) + 점수 (0~100) + 종합 판정. SRS 의 실현 가능성 사전 검증.

**입력:** SRS + 코드.

**산출물:** feasibility 보고서 + SRS 개선 제안.

**호출 예시:**
```
/snoworca-feasibility SRS_PATH=docs/spec/ CODE_PATH=src/
```

### 옵션 D. `kiwi-srs-feasibility`

**왜:** speckiwi MCP 활성 target SRS 전수 평가 + stability 일괄 갱신 (draft→evolving→stable→frozen). 본 SRS 의 stability 가 모두 미설정 상태이므로 적합.

**호출 예시:**
```
/kiwi-srs-feasibility
```
