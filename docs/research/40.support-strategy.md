# 4. Servlet 6.x 지원 전략

## 4.1 핵심 제약

- **단일 jar 로 5.0 / 6.0 / 6.1 을 모두 만족시킬 수 없다.** 사라진 시그니처(`encodeUrl`, `getSessionContext`, ...)를 보유한 클래스는 6.0 인터페이스를 implements 할 때 무해하지만, 새로 추가된 추상 메서드(`getRequestId` 등)를 구현하지 않으면 추상 클래스가 되어 컴파일 불가. 즉 **5.0 호환 클래스셋과 6.0 호환 클래스셋이 양립할 수 없다.**
- 컴파일 타깃이 분기된다 (5.0=Java 8, 6.0=Java 11, 6.1=Java 17).
- 사용자 입장에서는 **본인 환경의 servlet API 메이저 버전에 맞는 아티팩트 하나**를 선택할 수 있어야 한다.

## 4.2 옵션 비교

### 옵션 A. Multi-Release JAR (MRJAR)

`META-INF/versions/11/...` 디렉토리에 6.0 호환 클래스를 두는 방식.

**적합성: 부적합.**
- MRJAR 는 동일 클래스의 *서로 다른 바이트코드 버전*을 자바 버전에 따라 선택하는 메커니즘이지, 동일 클래스의 *서로 다른 의존성 버전(api 5 vs api 6)* 을 선택하는 메커니즘이 아니다.
- 사용자가 jakarta 5 컨테이너인지 6 컨테이너인지에 따라 다른 클래스가 로드되어야 하는데, MRJAR 는 JVM 버전만 본다.

### 옵션 B. Reflection / MethodHandle 추상화

위임 호출을 모두 `MethodHandles.lookup().findVirtual(...)` 로 변경.

**적합성: 부적합.**
- 어댑터의 본질은 **인터페이스를 implements** 하는 것이므로, 빌드 타임에 인터페이스 정의(어떤 추상 메서드가 있는지)를 알아야 한다. 리플렉션은 위임만 늦출 수 있지 인터페이스 충돌 자체를 해소하지 못한다.

### 옵션 C. Gradle source-set 분리 (단일 저장소, 다중 아티팩트)

`src/main/java` 외에 `src/jakarta6/java`, `src/jakarta61/java` source-set 추가. 공통 코드(Converter 류)는 `src/main`. 버전별 클래스(`adapter.jakarta.*`, `adapter.javax.*`)는 각 source-set 에서 재정의. publish 시 classifier (`-servlet5`, `-servlet6`, `-servlet61`) 또는 별도 아티팩트 ID 로 산출.

**적합성: 권장.**
- 단일 저장소에서 관리되어 변경이 동기화된다.
- 공통 코드(Converter 류, AsyncContext, Stream, Enum 변환)는 한 곳에서 유지된다 — 이들 클래스는 양쪽 API 모두 compileOnly 로 받으므로 5/6 어느 쪽에서든 그대로 컴파일된다 (단, 시그니처 변경된 메서드 호출이 없는 한).
- Gradle source-set 마다 `targetCompatibility` 를 독립 설정 가능.

**리스크:**
- `ServletAdapter` 진입점이 source-set 별로 분리되어야 하므로 사용자 코드는 그대로지만 내부 구현은 중복된다.
- `adapter.jakarta.*` 패키지가 source-set 마다 따로 빌드되어 같은 패키지명을 갖지만 각각 다른 jar 에 들어간다. 사용자는 한 번에 하나의 jar 만 의존해야 한다 (혼용 시 같은 클래스명 충돌).

### 옵션 D. 멀티 모듈 Gradle 프로젝트

`servlet-adapter-common` (Converter, 공통 enum 등) + `servlet-adapter-jakarta5`, `servlet-adapter-jakarta6`, `servlet-adapter-jakarta61` 서브프로젝트.

**적합성: 옵션 C 와 동급. 더 정석적이지만 보일러플레이트가 많다.**
- Maven Central 게시 시 사용자는 `servlet-adapter-jakarta6:0.x.x` 등 모듈을 선택해 의존.
- 모듈마다 build.gradle 이 분리되어 의존 매트릭스가 명확.

→ **본 프로젝트의 코드 규모(940 LOC)** 에서는 옵션 C 가 가볍고 충분.

### 옵션 E. Branch 분리

`servlet5`, `servlet6`, `servlet61` Git 브랜치로 관리.

**적합성: 부적합.**
- 공통 코드 변경 시 cherry-pick 부담이 커진다. 어댑터 코어가 발전할수록 분기 비용 누적.

## 4.3 권장 접근: 옵션 C 기반 단계적 적용

### Step 1. 코어/버전 종속 코드 분리

`src/main/java` 에 다음만 남긴다:
- `com.snoworca.ServletAdapter` 인터페이스 (또는 abstract)
- `adapter.servletElementConverter.*` 중 시그니처 변경에 영향 없는 변환기 (Stream, AsyncContext 등 — 단, 양쪽 API 인터페이스 호출이 없는 순수 유틸 위주)

→ 실제로는 Converter 들도 jakarta 5/6 인터페이스를 모두 참조하므로, source-set 마다 사본을 두는 것이 단순하다. 무리한 추출은 피하자.

### Step 2. source-set 추가

```groovy
sourceSets {
    main { java.srcDirs = ['src/main/java'] }
    jakarta6 {
        java.srcDirs = ['src/jakarta6/java']
        compileClasspath += sourceSets.main.output  // common 활용 시
    }
    jakarta61 {
        java.srcDirs = ['src/jakarta61/java']
    }
}

configurations {
    jakarta6CompileOnly.extendsFrom compileOnly
    jakarta61CompileOnly.extendsFrom compileOnly
}

dependencies {
    // 기존 5.0 라인은 그대로
    compileOnly 'javax.servlet:javax.servlet-api:4.0.1'
    compileOnly 'jakarta.servlet:jakarta.servlet-api:5.0.0'

    jakarta6CompileOnly 'javax.servlet:javax.servlet-api:4.0.1'
    jakarta6CompileOnly 'jakarta.servlet:jakarta.servlet-api:6.0.0'

    jakarta61CompileOnly 'javax.servlet:javax.servlet-api:4.0.1'
    jakarta61CompileOnly 'jakarta.servlet:jakarta.servlet-api:6.1.0'
}

java {
    // 5.0 모듈
    sourceCompatibility = '1.8'
    targetCompatibility = '1.8'
}

tasks.named('compileJakarta6Java') {
    options.release.set(11)
}
tasks.named('compileJakarta61Java') {
    options.release.set(17)
}

task jakarta6Jar(type: Jar) {
    archiveClassifier = 'servlet6'
    from sourceSets.jakarta6.output
}
task jakarta61Jar(type: Jar) {
    archiveClassifier = 'servlet61'
    from sourceSets.jakarta61.output
}
artifacts {
    archives jakarta6Jar
    archives jakarta61Jar
}
```

### Step 3. 6.0 source-set 에 변경 적용

`src/jakarta6/java` 에 `src/main/java` 의 사본을 두고 [30.compatibility-impact.md](30.compatibility-impact.md) §3.1, §3.2.2 에 정리된 항목을 적용:

1. `adapter.jakarta.servlet.http.HttpSessionContext.java` — **삭제**
2. `adapter.jakarta.servlet.http.HttpSession` — 5개 메서드 제거
3. `adapter.jakarta.servlet.http.HttpServletRequest` — `isRequestedSessionIdFromUrl` 제거
4. `adapter.jakarta.servlet.http.HttpServletResponse` — `encodeUrl`, `encodeRedirectUrl`, `setStatus(int,String)` 제거
5. `adapter.jakarta.servlet.ServletContext` — `log(Exception, String)` 제거
6. `adapter.jakarta.servlet.ServletRequest` — `getRequestId`, `getProtocolRequestId`, `getServletConnection` 신규 구현
7. (선택) `adapter.javax.servlet.http.Cookie` — 6.0 Cookie 의 attribute API 손실 처리. javax → jakarta 변환 시 무영향(javax 측에 없음). jakarta → javax 변환 시에는 `adapter.javax.servlet.http.Cookie` 가 javax 4.0 Cookie 를 implements 하므로 attribute 정보를 보존하는 별도 Map 필드를 추가하고, `addCookie` 시 응답 헤더에 합성하는 방식으로 일부 보존 가능.

### Step 4. 6.1 source-set 에 증분 적용

`src/jakarta61/java` 는 `src/jakarta6/java` 의 사본에서:
1. `HttpServletResponse` 의 `sendRedirect` 오버로드 3종 — jakarta 6.1 인터페이스의 default 구현으로 충분하다면 별도 작업 불필요. 양방향 위임이 명시적으로 필요하면 추가.
2. `HttpServlet.isSensitiveHeader` — 어댑터가 HttpServlet 을 직접 구현하지 않으므로 무관.

→ 6.0 과 6.1 간 차이는 미미하므로 **단일 source-set (`jakarta6`) 으로 6.0/6.1 양쪽을 커버**하는 것도 검토 가치가 있다. 결정 기준은 6.1 신규 시그니처를 어댑터 사용자에게 명시적으로 노출할 것인지. 노출하지 않으면 단일 source-set 으로 충분 (Java 11 타깃으로 빌드한 jar 가 Java 17 컨테이너에서도 동작).

### Step 5. 진입점(ServletAdapter) 통일

각 source-set 에 동일 패키지·동일 클래스명의 `com.snoworca.ServletAdapter` 를 둔다. 사용자는 본인 환경에 맞는 classifier 의 jar 하나만 의존하면 된다.

### Step 6. 산출물 게시

Maven Central 게시 시:
- 기본 jar: `Jakarta_To_Javax_Servlet_Adapter-0.x.x.jar` (5.0)
- classifier jar: `-servlet6.jar`, `-servlet61.jar`

또는 별도 artifactId 권장:
- `jakarta-to-javax-servlet-adapter` (5.0)
- `jakarta-to-javax-servlet-adapter-servlet6` (6.0+)
- `jakarta-to-javax-servlet-adapter-servlet61` (6.1)

후자가 Maven 사용자에게 더 직관적이다.

## 4.4 테스트 전략

- 현재 테스트는 `src/test/java/com/snoworca/Servlet*Test.java` 2개 파일. Mockito 기반.
- source-set 별로 별도 test source-set 을 만든다: `src/jakarta6Test/java`, `src/jakarta61Test/java`.
- 핵심 검증 항목:
  - 컴파일 자체가 통과해야 함 (인터페이스의 모든 추상 메서드 구현).
  - mock jakarta 6.0 `HttpServletRequest` 를 어댑터로 감싸 javax 4.0 호출이 위임되는지 확인.
  - `HttpSession.getValue/putValue` 가 jakarta 6.0 에 없으므로, javax 측 호출 시 `UnsupportedOperationException` 또는 attribute API fallback 동작 검증.
  - 통합 테스트는 가능하다면 Tomcat 10.1 / 11 임베드해 servlet 등록 → HTTP 요청까지 검증 권장.

## 4.5 점진적 로드맵

| Phase | 작업 | 산출물 |
|---|---|---|
| P1 | Servlet 5.0 코드 동결 + 단위 테스트 보강 | 안정 베이스라인 |
| P2 | Gradle source-set `jakarta6` 추가, 5.0 코드 사본 후 컴파일 가능하게 정리 | 컴파일만 통과하는 servlet 6 모듈 |
| P3 | 6.0 신규 시그니처(`getRequestId` 등) 구현 + Cookie attribute 정책 결정 | 기능 완성된 servlet 6 모듈 |
| P4 | jakarta 6.0 mock 기반 테스트 추가 | 테스트 그린 |
| P5 | (선택) `jakarta61` source-set 분리 또는 6.0 모듈로 6.1 커버 결정 | servlet 6.1 모듈 또는 단일화 |
| P6 | Maven Central artifact 분리·게시 | 사용자가 버전 선택 가능 |

## 4.6 의사 결정 포인트 (사용자 확인 필요)

본 연구는 코드 변경을 하지 않는다. 실제 구현 착수 전 다음 결정이 필요하다:

1. **6.0 만 지원할지, 6.1 까지 지원할지.** 6.1 신기능(`sendRedirect` 오버로드, 새 상태 상수) 노출 가치를 사용자 베이스가 요구하는가?
2. **Cookie attribute API 손실 처리 정책.** 손실 허용 + 문서 안내 vs. 자체 attribute Map + Set-Cookie 합성.
3. **Servlet 5.0 라인 동결 시점.** 6.x 라인에 합류시키지 않고 별도 유지보수 라인으로 둘지, 5.0 지원 자체를 폐기할지.
4. **Java 11/17 빌드 환경 확보.** 현재 빌드 환경이 어느 JDK 인지, CI 에서 멀티 JDK 빌드가 가능한지.
5. **Artifact 명명 규칙.** classifier 사용 vs. 별도 artifactId 분리.
