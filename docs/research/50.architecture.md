# 어댑터 모듈 분리 아키텍처 재설계 — 심층 연구

## 0. 연구 범위와 결론 요약

본 문서는 `Jakarta_To_Javax_Servlet_Adapter` 모듈을 Jakarta Servlet **5.0 / 6.0 / 6.1** 모두 지원하도록 재구조화하기 위한 **아키텍처 측면의 의사결정 자료**다. 코드 변경은 일절 수행하지 않았으며, 변환 로직 자체의 정확성(다른 에이전트 담당)은 다루지 않는다.

핵심 권장은 다음과 같다 — 각 결정의 근거는 본문에서 상술한다.

| 결정 항목 | 권장안 |
|---|---|
| 토폴로지 | **multi-module Gradle 프로젝트** (`common`, `servlet5`, `servlet6`, `servlet61`, 옵션으로 `bom`) |
| 공통 코드 분리 | `EnumsConverter`, `HttpComponentConverter`, `ReadListenerConverter`, `WriteListenerConverter`, `StreamConverter`, `DescriptorConverter` 의 일부는 `common` 으로 — 단 **common 의 jakarta API 의존을 5.0 으로 핀**해 하위 호환 보장 |
| 패키지 네이밍 | **(b) 버전 구분 패키지**: `adapter.jakarta.servlet5.*`, `adapter.jakarta.servlet6.*`, `adapter.jakarta.servlet61.*` (또는 동등하게 `adapter.javax.servlet5.*` 등). `common` 은 `adapter.common.*` |
| 진입점 | `com.snoworca.ServletAdapter` 는 **버전별 모듈에 각각 동일 클래스명·동일 패키지로** 두되, 사용자가 양 버전을 동시에 임베드하는 시나리오를 위해 **각 모듈에 `ServletAdapter5`, `ServletAdapter6`, `ServletAdapter61` 별칭 진입점도 추가** |
| Java 타깃 | 5.0=Java 8 / 6.0=Java 11 / 6.1=Java 17 / common=Java 8 |
| Artifact 게시 | `artifactId` 분리(`-servlet5`, `-servlet6`, `-servlet61`) + BOM 모듈 |
| Java Platform Module System(JPMS) | **현 단계에서는 도입하지 않음** — `module-info.java` 는 향후 옵션 |
| 패키지 간 의존 방향 | `common ← servlet5`, `common ← servlet6`, `common ← servlet61`. 버전 모듈 간 상호 의존 금지 |
| 사용자 마이그레이션 | `0.x → 1.0` 전환 시점에 패키지명 변경 동시 단행, 0.x 라인은 `servlet5` 호환 alias artifact 유지 (1년) |

이하 본문에서 Q1~Q10 을 차례로 답한다.

## 1. Q1. 모듈 분리 토폴로지 — multi source-set vs multi-module

### 1.1 비교 축

| 평가 축 | 단일 프로젝트 + multi source-set | multi-module Gradle 프로젝트 |
|---|---|---|
| 보일러플레이트 | 적음 (단일 `build.gradle`) | 많음 (모듈마다 `build.gradle`) |
| Gradle 의존 그래프 가시성 | 낮음 — 한 파일에 `compileJakarta6Java`, `compileJakarta61Java` 등 태스크가 섞여서 분기됨 | 높음 — `:servlet6:compileJava` 처럼 모듈별 구분이 명확 |
| Java 타깃 분기 | 가능하나 `tasks.named('compileXxx').options.release.set(11)` 로 우회 필요 | 자연 — 각 서브프로젝트에 `java.targetCompatibility` 만 두면 됨 |
| 의존성 격리 | 약함 — source-set 들이 같은 프로젝트의 `compileClasspath` 를 부분 상속해 누수 가능 | 강함 — 서브프로젝트 경계가 곧 의존성 경계 |
| 테스트 분리 | 별도 test source-set 추가 필요 (수동) | 자연 — 각 서브프로젝트에 `src/test/java` 자동 |
| CI 매트릭스 빌드 | 단일 task 그래프이므로 `./gradlew build` 가 모든 source-set 빌드, JDK 분기는 toolchain 이 흡수 | 동일하게 `./gradlew build` 로 전체 빌드, 게다가 `./gradlew :servlet6:build` 같은 부분 빌드가 자연 |
| Maven Central 게시 | `maven-publish` 의 `publications` 안에서 classifier 별로 분기, 또는 별도 `publication` 추가 | 모듈마다 `publishing` 블록 — 직관적 |
| 사용자 의존 표현 | classifier 의존(`implementation "...:0.x:servlet6"`) — Gradle/Maven 양쪽에서 가능하나 흔치 않음 | artifactId 분리(`implementation "com.clipsoft:jakarta-to-javax-servlet-adapter-servlet6:0.x"`) — 표준적 |
| 향후 6.2 / 7 추가 | source-set 1개 추가, `compileJakarta62Java` 태스크 분기 — 점점 복잡 | 모듈 1개 추가 — 일정 비용 |

### 1.2 정량 근거

코드 LOC 현황은 다음과 같다 (실측, `wc -l`).

| 디렉토리 | LOC |
|---|---|
| `src/main/java/adapter/jakarta` | 1,501 |
| `src/main/java/adapter/javax` | 1,669 |
| `src/main/java/adapter/servletElementConverter` | 1,285 |
| `src/main/java/com/snoworca` (ServletAdapter) | 80 |
| **합계** | **4,535** |

기존 연구 문서 `docs/research/40.support-strategy.md:52` 에서 940 LOC 라고 했던 수치는 *기능 핵심부* 만 센 추정치로 보이며, 실제로는 4.5K LOC 규모다.

- Source-set 분리 시 — `src/jakarta6/java` 와 `src/jakarta61/java` 가 각각 **3,170+ LOC**(jakarta + javax 측 사본) 를 복제. 단일 프로젝트의 `src` 트리에 약 12K LOC가 응집한다. IDE 가독성·git diff 가독성 모두 저하된다.
- Multi-module — 같은 LOC가 `servlet5/`, `servlet6/`, `servlet61/` 으로 분배되어 각 모듈 ~3.2K LOC. **각 모듈이 독립적으로 IntelliJ Project view 의 한 화면에 들어온다.** 또한 공통 코드(Converter)는 `common/` 에 ~600 LOC 정도 남아 한 모듈로 응집한다.
- 6.0 → 6.1 의 *증분* 변경은 `docs/research/40.support-strategy.md:142-147` 에서도 "단일 source-set 으로 6.0/6.1 양쪽을 커버하는 것도 검토 가치가 있다"고 인정한 만큼 작다. 그럼에도 별도 모듈로 분리할 가치는 **artifact 분리** 와 **사용자에게 6.1 노출 명시성** 에 있다.

### 1.3 권장: multi-module

근거 요약:

1. 4.5K LOC 라는 규모와 3개 타깃 jakarta 버전 + 1개 common 의 4개 단위가, source-set 1개 프로젝트로 응집하기에는 복잡도가 충분히 크다.
2. **타깃 Java 버전이 모듈마다 다르므로(8/11/17)** 모듈별 `targetCompatibility` 단일 설정이 가장 깔끔하다. source-set 방식은 동일 프로젝트 안에서 8/11/17 컴파일 옵션을 분기시키므로 IDE 가 잘못 잡으면 5.0 코드가 17 API 를 호출해도 한참 뒤에 빌드에서 잡힌다.
3. 사용자 입장에서 `artifactId` 가 분리되어 있으면 Maven Repository 페이지에서 즉시 어떤 버전을 받는지 알 수 있다(classifier 방식은 사용자가 명시적으로 `<classifier>` 를 적어야 함).
4. 향후 Servlet 6.2 / 7 / javax 3.x 같은 새 타깃이 추가될 때 모듈 1개를 추가하는 것이 단일 `build.gradle` 안에 source-set 을 또 끼워넣는 것보다 단순하다.

## 2. Q2. common 에 들어갈 수 있는 코드의 정확한 식별

### 2.1 각 컨버터 클래스 분류표

`src/main/java/adapter/servletElementConverter` 의 9개 클래스를 모두 분석한 결과는 다음과 같다.

| 클래스 | jakarta API 의존 | javax API 의존 | 영향받는 시그니처 변경 (5→6) | common 이전 가능? |
|---|---|---|---|---|
| `ServletReqResConverter` | `ServletRequest`, `ServletResponse` (양방향 변환의 핵심) | 동일 | 직접적 시그니처 변경 없음. 단 내부에서 `adapter.jakarta.servlet.http.HttpServletRequest` 등 **버전별 어댑터 클래스** 를 `new` 함 → **버전별** | **불가** (버전별 어댑터 클래스 인스턴스화 책임) |
| `ServletConverter` (529 LOC, 가장 큼) | `Servlet`, `Filter`, `FilterChain`, `Registration`, `ServletConfig`, `FilterConfig`, `SessionCookieConfig`, `MultipartConfigElement`, `ServletSecurityElement`, `HttpMethodConstraintElement`, `annotation.ServletSecurity.*` | 모두 동일 (mirror) | `SessionCookieConfig.setComment/getComment` 는 6.1에서 `forRemoval=true` 유지 / 그 외 5.0 시그니처 그대로 — 컴파일은 통과하나 deprecation 경고 다수 | **불가** (양쪽 API 인터페이스 다수를 implements/anonymous 로 호출) |
| `StreamConverter` | `ServletInputStream`, `ServletOutputStream`, `ReadListener`, `WriteListener` | 동일 | 5→6 시그니처 변경 없음. `setReadListener/setWriteListener` 인터페이스는 5.0/6.0/6.1 동일 | **불가** (인터페이스 메서드 직접 구현 — 6.0 API 가 5.0과 동일 추상 메서드 셋이라는 점은 사실이나, 잘못된 5.0 인터페이스를 implements 한 익명 클래스 객체는 6.0 jar 에서 *형식상 다른 타입* 으로 인식되므로 결국 모듈마다 재컴파일 필요) |
| `DescriptorConverter` | `descriptor.JspConfigDescriptor`, `JspPropertyGroupDescriptor`, `TaglibDescriptor` | 동일 | 5→6 시그니처 변경 없음. 6.0 에서도 descriptor 인터페이스는 그대로 | **불가** (위와 동일 이유로 모듈마다 재컴파일 필요) |
| `AsyncContextConverter` | `AsyncContext`, `AsyncListener`, `AsyncEvent`, `ServletContext`, `ServletRequest`, `ServletResponse`, `ServletException` | 동일 | `AsyncContext.hasOriginalRequestAndResponse()` 는 어차피 5.0에도 존재. 6.0 에서 시그니처 변경 없음 | **불가** |
| `EnumsConverter` | `SessionTrackingMode` (값 매핑) | `SessionTrackingMode` | `SessionTrackingMode` 의 enum 상수(`URL`, `SSL`, `COOKIE`) 는 5/6/6.1 모두 동일 | **조건부 가능** — Q2.2 참조 |
| `HttpComponentConverter` | `DispatcherType` | `DispatcherType` | enum 상수 5/6/6.1 동일 | **조건부 가능** |
| `ReadListenerConverter` | `ReadListener` | `ReadListener` | `ReadListener` 의 3개 메서드(`onDataAvailable`, `onAllDataRead`, `onError`) 는 5/6/6.1 동일 | **조건부 가능** |
| `WriteListenerConverter` | `WriteListener` | `WriteListener` | `WriteListener` 의 2개 메서드(`onWritePossible`, `onError`) 는 5/6/6.1 동일 | **조건부 가능** |

### 2.2 핵심 통찰 — "시그니처 변경 면역" ≠ "common 안전"

위 표에서 "조건부 가능"으로 표시한 4개 컨버터(`EnumsConverter`, `HttpComponentConverter`, `ReadListenerConverter`, `WriteListenerConverter`)는 **호출하는 jakarta API 시그니처 자체는 5/6/6.1 동일** 하다. 그러나 다음 두 제약이 있다.

**제약 A — 익명 클래스 생성 자체가 컴파일 시점의 jakarta 인터페이스에 바인딩된다.**

예시: `ReadListenerConverter.convert(jakarta.servlet.ReadListener readListener)` 가 반환하는 `new javax.servlet.ReadListener() { ... }` 익명 객체는 javax 인터페이스를 implements 한다. 이 익명 클래스의 바이트코드는 javax 인터페이스 정의에 의존(`InnerClasses` attribute). 만약 common 모듈이 jakarta 5.0 으로 컴파일된 `javax.servlet.ReadListener` 추상 메서드 시그니처를 기준으로 익명 클래스를 만들었는데, jakarta 6.x 에서 `ReadListener` 인터페이스에 새 추상 메서드가 추가된다면, 이 익명 클래스는 6.x 런타임에서 `AbstractMethodError` 를 던진다.

→ 다행히 `ReadListener` / `WriteListener` / `DispatcherType` / `SessionTrackingMode` 는 **5.0 / 6.0 / 6.1 모두 추상 메서드 / enum 상수 셋이 변경 없음**. 따라서 common 에 둘 수 있다.

**제약 B — javax 4.0 측은 영구 고정이라 양쪽 모두 의존 가능한 common 은 5.0 jakarta 만 import 해도 6.x 환경에서 동작한다 (단, ABI 호환성이 유지되는 한).**

Jakarta Servlet 5.0 ↔ 6.0 사이의 ABI 호환성은 *추가/제거된 추상 메서드* 가 핵심 깨짐 요인이다. `ReadListener` / `WriteListener` / `DispatcherType` / `SessionTrackingMode` 는 깨지지 않는다. 따라서 다음 전략이 가능하다.

> **common 모듈은 jakarta 5.0 + javax 4.0 만 compileOnly 의존으로 가진다. 단 common 코드는 5/6/6.1 사이 ABI 변경이 없는 심볼만 참조하도록 신중히 작성한다.**

이 정책 하에서 common 에 둘 수 있는 클래스는:

- `EnumsConverter` — `SessionTrackingMode` enum 상수 5/6/6.1 동일
- `HttpComponentConverter` — `DispatcherType` enum 상수 5/6/6.1 동일
- `ReadListenerConverter` — `ReadListener` 추상 메서드 셋 5/6/6.1 동일
- `WriteListenerConverter` — `WriteListener` 추상 메서드 셋 5/6/6.1 동일
- 추가로 도입할 헬퍼: `ConverterSupport` (예외 wrapping — `wrapJakartaException(javax.servlet.ServletException) → jakarta.servlet.ServletException` 같은 패턴이 반복되므로 추출 가치)

common 에 둘 수 **없는** 것:

- `ServletReqResConverter` — 버전별 어댑터 클래스명(`adapter.jakarta.servlet5.http.HttpServletRequest` 등) 을 직접 참조해야 함. 버전마다 `new` 대상이 다르므로 버전별 모듈로 강제 분리.
- `ServletConverter` — `SessionCookieConfig.setComment` 가 5.0에 존재(deprecated)지만 6.x 에서 `forRemoval=true` 로 유지된다. 미래 7.x 에서 제거될 가능성 있어 common 에 두면 7.x 지원 시 깨진다. 또한 다수 인터페이스를 익명 implements 하므로 ABI 누수 위험 큼.
- `StreamConverter` — `ServletInputStream`, `ServletOutputStream` 는 5/6/6.1 동일하나, **내부에서 `ReadListenerConverter` 와 `WriteListenerConverter` 를 호출**한다. common 의 동일 클래스를 호출하면 되니 기술적으로 common 으로 옮길 수도 있다. 그러나 `setReadListener` 의 인자 타입이 버전별로 다른 패키지로 박혀 있어 미세한 양립성 검토 필요. 보수적으로는 버전별 모듈에 두고 common 의 ReadListenerConverter 만 호출한다.
- `DescriptorConverter` — descriptor 인터페이스가 5/6/6.1 동일이지만 다수 메서드의 익명 implements 라 ABI 노출. 보수적으로 버전별로 둔다.
- `AsyncContextConverter` — `ServletContext` 익명 호출 등 다수 인터페이스 참조. 버전별.

### 2.3 common 의 jakarta API 의존 버전 결정

세 버전 모두를 만족하는 jakarta API 버전을 단일 선택해야 한다.

| 선택 | 장점 | 단점 |
|---|---|---|
| **jakarta.servlet-api:5.0.0** | 가장 보수적. 5/6/6.1 모두에 존재하는 심볼만 사용 가능 | 6.0+ 신 시그니처(`Cookie.setAttribute` 등) 를 common 에서 호출 불가 — 그러나 그런 호출이 필요하면 어차피 버전별 모듈로 옮겨야 하므로 무해 |
| jakarta.servlet-api:6.0.0 | 신 API 사용 가능 | 5.0 모듈에서 common 의 익명 클래스가 6.0 인터페이스로 컴파일되면 5.0 런타임에 `AbstractMethodError` 위험. **금지** |
| jakarta.servlet-api:6.1.0 | 최신 | 5.0/6.0 양쪽에서 동작 보장 안 됨. 금지 |

→ **결론: common 의 jakarta 의존은 5.0.0 으로 핀.**

```groovy
// common/build.gradle
dependencies {
    compileOnly 'javax.servlet:javax.servlet-api:4.0.1'
    compileOnly 'jakarta.servlet:jakarta.servlet-api:5.0.0'
}
java { sourceCompatibility = JavaVersion.VERSION_1_8; targetCompatibility = JavaVersion.VERSION_1_8 }
```

이 핀은 향후 *5.0의 LTS 적 위상* 이 변하지 않는 한 안정적이다. 만약 Jakarta Servlet 5.0 자체에서 새 deprecation 이 forRemoval 단계로 진입하는 일이 생기면 그때 다시 평가.

### 2.4 common 으로 옮긴 후 LOC 추정

- `EnumsConverter` 25 LOC
- `HttpComponentConverter` 23 LOC
- `ReadListenerConverter` 46 LOC
- `WriteListenerConverter` 37 LOC
- 신규 `ConverterSupport` 추정 ~80 LOC

→ common ≈ **210 LOC**. 나머지 1075 LOC 의 컨버터는 버전별 3개 모듈로 사본 분배된다 (사본 비용 = 1075 × 3 ≈ 3225 LOC 사본). **사본 비용이 크다고 느낄 수 있으나** 양립성과 유지보수성 양면에서 합리적 비용이다 — 6.x 라인이 5.0 의 `SessionCookieConfig.setComment` 같은 deprecated 호출을 떨어내는 작업은 어차피 버전별 사본에서만 일어나야 하기 때문이다.

### 3.2 권장: (b)

근거:

1. **사용자가 두 버전을 동시에 임베드하는 시나리오는 충분히 현실적**이다. 예: 마이그레이션 중인 게이트웨이가 한 JVM 안에서 Tomcat 10.0 와 Tomcat 10.1 양쪽 객체를 변환해야 하는 경우. (a) 는 이 시나리오를 원천 차단한다. 본 어댑터의 목적이 *변환* 인 만큼 이 시나리오는 핵심 사용처일 수 있다.
2. (c) 의 `com.snoworca.servlet5.adapter.jakarta.servlet.*` 형태는 길고, 사용자가 패키지 prefix(`com.snoworca.servlet5`) 와 콘텐츠(`adapter.jakarta.servlet`) 의 관계를 즉시 파악하기 어렵다.
3. (d) JPMS 는 jakarta servlet 6.0+ 가 자체적으로 module 화되어 있지 않다(2024-2026 기준 자동 모듈 명만 제공). 본 어댑터에 `module-info.java` 를 강제하면 비-JPMS 클래스패스 사용자가 손해를 본다.
4. (b) 의 패키지 갈래는 `adapter.jakarta.servlet5.*` vs `adapter.jakarta.servlet6.*` 같이 *눈에 띄게 다르므로* 사용자가 어느 버전의 어댑터를 사용 중인지 import 만 봐도 안다 — 유지보수성 향상.

## 4. Q4. 사용자 진입점 통일 vs 분리

### 4.1 시그니처 차이 분석

현재 `com.snoworca.ServletAdapter` (src\main\java\com\snoworca\ServletAdapter.java:12-79) 는 모든 메서드가 정적이며 jakarta 5.0 타입을 반환한다.

```java
public static jakarta.servlet.http.HttpServletResponse adaptToJakarta(javax.servlet.http.HttpServletResponse response) {
    return new adapter.jakarta.servlet.http.HttpServletResponse(response);
}
```

여기서 반환 타입 `jakarta.servlet.http.HttpServletResponse` 는 5.0 / 6.0 / 6.1 *각자 다른 인터페이스 정의* 다. 사용자 코드는 다음과 같이 작성된다.

```java
jakarta.servlet.http.HttpServletResponse jakartaResp = ServletAdapter.adaptToJakarta(javaxResp);
jakartaResp.encodeRedirectURL(url);  // 5.0 에는 있는 시그니처, 6.0 에서도 존재
jakartaResp.encodeRedirectUrl(url);  // 5.0 에는 deprecated 로 존재, 6.0 에서는 제거 — 사용자 코드 컴파일이 jakarta 버전에 따라 갈림
```

→ **반환 타입은 `jakarta.servlet.http.HttpServletResponse` 로 같지만**, 사용자가 그 객체에 어떤 메서드를 호출할 수 있는지는 *사용자 환경의 jakarta-servlet-api* 가 결정한다. 따라서 어댑터 모듈은:

- 어떤 jakarta 버전 인터페이스를 *implements 하느냐* 만 차이.
- 진입점의 시그니처 자체는 모든 버전에서 동일하게 `jakarta.servlet.http.HttpServletResponse` 를 반환.

이 점이 본 어댑터를 "버전별 모듈로 분리하되 사용자 코드는 그대로 둘 수 있는" 구조로 만든다.

### 4.2 양 버전 동시 사용 시나리오

> 사용자가 한 JVM 안에서 jakarta 5.0 컨테이너와 jakarta 6.0 컨테이너를 동시에 임베드하는 게이트웨이가 있다고 하자.

이 경우 클래스패스에 *두 가지 jakarta-servlet-api 가 동시에 존재할 수 없다*. JVM 은 같은 FQCN(`jakarta.servlet.http.HttpServletResponse`) 의 클래스를 한 번만 로드한다. 두 jar 를 같은 클래스로더에 올리면 둘 중 하나만 활성화되고 다른 쪽은 무력화된다.

따라서 **양 버전 동시 사용 시나리오는 클래스로더 분리(ParentLastClassLoader, OSGi 등) 가 전제**다. 이 경우 어댑터 모듈도 두 ClassLoader 에 각각 로드되는 두 인스턴스로 존재하게 된다 — 어댑터 입장에서는 따로 처리할 일이 없다 (각자 격리).

그렇다면 사용자에게 `ServletAdapter5`, `ServletAdapter6` 별칭을 제공할 필요가 있는가?

- **단일 ClassLoader 시나리오**: 한 jakarta 버전만 쓰는 경우. `ServletAdapter` 하나로 충분.
- **다중 ClassLoader 시나리오**: 사용자가 ClassLoader 격리를 한다. 어댑터를 두 번 로드. 호출 측에서 적절한 ClassLoader 의 `ServletAdapter` 를 호출하면 됨 — 클래스명 충돌은 ClassLoader 가 격리.
- **클래스로더 격리 없이 reflection 으로 양쪽 다 호출** 하는 변종 시나리오: 사용자가 `Class.forName("com.snoworca.servlet5.ServletAdapter5")` 식으로 부르는 게 편함.

→ 결론: **별칭 진입점 `ServletAdapter5` / `ServletAdapter6` / `ServletAdapter61` 추가 제공**. 보통 사용자는 `ServletAdapter` 만 쓰고, 별칭은 reflection 시나리오 사용자를 위한 보조.

### 4.3 권장 진입점 API

`servlet5` 모듈 (요약):

```java
package com.snoworca;

@SuppressWarnings("unused")
public final class ServletAdapter {
    private ServletAdapter() {}

    // 5.0 어댑터 모듈에서는 5.0 jakarta 인터페이스 반환
    public static jakarta.servlet.http.HttpServletResponse adaptToJakarta(javax.servlet.http.HttpServletResponse r) {
        return new adapter.jakarta.servlet5.http.HttpServletResponse(r);
    }
    // ...
}
```

```java
package com.snoworca;

/** 5.0 전용 별칭 진입점 — 다른 jakarta 버전 ServletAdapter 와 동일 JVM 에 공존하는 시나리오 대비. */
public final class ServletAdapter5 {
    private ServletAdapter5() {}
    public static jakarta.servlet.http.HttpServletResponse adaptToJakarta(javax.servlet.http.HttpServletResponse r) {
        return ServletAdapter.adaptToJakarta(r);
    }
    // ... 모든 메서드를 ServletAdapter 로 위임. 컴파일 타임에 5.0 jakarta-servlet-api 를 가리킴.
}
```

`servlet6` 모듈도 동일한 패키지/클래스명으로 둠. 사용자가 `ServletAdapter5` 와 `ServletAdapter6` 둘 다 한 코드에서 import 하면 *클래스로더 격리 없이는 동시 동작 불가* 라는 한계를 README 에 명시.

## 6. Q6. 패키지 간 의존 방향 규칙

### 6.1 의존 그래프

```
                       common
                         ▲
        ┌────────────────┼────────────────┐
        │                │                │
     servlet5         servlet6         servlet61
        │                │                │
        ▼                ▼                ▼
    (사용자)          (사용자)          (사용자)
```

- **common ← servlet5 / servlet6 / servlet61**: 모든 버전 모듈이 common 에 의존. common 은 어디에도 의존하지 않음 (jakarta/javax 외).
- **servlet5 ↔ servlet6 ↔ servlet61**: 서로 의존하지 않는다. 의존하게 되면 한 모듈의 jakarta API 버전이 다른 모듈로 새어들어가 컴파일 충돌이 발생할 위험.
- **각 버전 모듈 → common 의존은 `api`** 로 선언. 사용자가 servlet6 만 import 했을 때 common 의 `EnumsConverter` 같은 심볼이 transitive 로 보이도록.

### 6.2 충돌 가능성 분석

- **이론적**: `servlet5` 가 common 의 `EnumsConverter` 를 호출한다 → common 의 `EnumsConverter` 는 `jakarta.servlet.SessionTrackingMode` 라는 클래스를 참조. 이 클래스는 `servlet5` 컴파일 시점에는 jakarta-servlet-api:5.0 의 것이고, `servlet6` 컴파일 시점에는 6.0 의 것이다. 하지만 enum 상수가 같으므로 양쪽 모두 동작.
- **검증해야 할 ABI 항목**: `SessionTrackingMode`, `DispatcherType`, `ReadListener`, `WriteListener` 의 추상 메서드 셋이 5/6/6.1 동일하다는 점. Q2.2 에서 확인.
- **만약 미래 7.0 에서 `ReadListener` 가 새 추상 메서드를 추가하면**: common 의 `ReadListenerConverter.convert()` 가 만든 익명 클래스가 새 추상 메서드를 구현하지 않게 되어 `AbstractMethodError`. 그때는 common 의 해당 컨버터를 버전별 모듈로 이전(downgrade)하거나, common 의 jakarta API 핀을 5.0 → 7.0 으로 올린 별도 common71 모듈을 신설하는 등 대응.

### 6.3 ServletAdapter 진입점이 common 에 들어갈 수 있는가?

**불가**. 이유:

1. `ServletAdapter.adaptToJakarta(javax.servlet.http.HttpServletResponse)` 는 *어떤 버전의* `adapter.jakarta.servlet[N].http.HttpServletResponse` 를 `new` 할지 결정해야 한다 — 즉 버전별 어댑터 클래스를 참조한다.
2. common 은 버전별 모듈을 *모르고* 있어야 한다 (반대 방향). 그러지 않으면 common ← servletN 의 단방향 의존 그래프가 깨진다.

따라서 `ServletAdapter` 는 **버전별 모듈 각각에 동일 패키지(`com.snoworca`)·동일 클래스명으로 둔다**. 코드 중복이 발생하지만, 본 어댑터에서 ServletAdapter 의 본체는 단순 위임이라 중복이 80 LOC × 3 = 240 LOC 정도로 작다.

> **대안 검토**: common 에 인터페이스 `ServletAdapterSpi` 를 두고 버전별 모듈이 구현체를 `META-INF/services` 로 등록 → ServiceLoader 로 로딩? 가능하나 정적 메서드 호출이라는 단순한 사용자 API 가 깨진다. 사용자 코드가 `ServletAdapter.adaptToJakarta(...)` 를 `ServiceLoader.load(...)` 로 바꿔야 함. → **부적합. 위임 중복을 감내**.

## 8. Q8. 향후 확장성

### 8.1 Servlet 6.2 추가 시나리오

- Jakarta Servlet 6.2 가 EE 12 와 함께 출시된다고 가정. 6.1 → 6.2 는 6.0 → 6.1 처럼 증분 릴리즈로 추정.
- **방법**: `servlet62` 모듈 신설.

```groovy
// settings.gradle 에 추가
include 'servlet62'
```

```groovy
// servlet62/build.gradle (servlet61 사본에서 6.1 → 6.2 만 교체)
archivesBaseName = 'jakarta-to-javax-servlet-adapter-servlet62'

    toolchain { languageVersion = JavaLanguageVersion.of(21) }  // EE12 가 Java 21 LTS 기준이라 가정
    sourceCompatibility = JavaVersion.VERSION_21
    targetCompatibility = JavaVersion.VERSION_21
}
dependencies {
    api project(':common')
    compileOnly 'javax.servlet:javax.servlet-api:4.0.1'
    compileOnly 'jakarta.servlet:jakarta.servlet-api:6.2.0'
}
```

`src/main/java/adapter/jakarta/servlet62/...` 등으로 클래스 사본. 통상 코드 사본 + 신규 시그니처 추가만으로 완성.

비용 추정: 6.1 → 6.2 가 증분이라면 ~1주.

### 8.2 Jakarta Servlet 7 추가 시나리오

- 7.0 은 또 다른 메이저 컷오프(deprecated 일괄 제거 가능성). 6.0 → 7.0 의 영향은 6.0 의 deprecated (예: `SessionCookieConfig.setComment`, `Cookie.getComment/getVersion`) 가 *제거* 될 가능성.
- **방법**: `servlet7` 모듈 신설. common 에 영향이 있는지 검토 (예: `EnumsConverter` 가 `SessionTrackingMode` 의 상수를 호출하는데, 7.0 에서 enum 상수가 변하면 common 에 둘 수 없게 됨).
- common 의 jakarta 핀이 5.0 인 한, 7.0 모듈도 common 의 `EnumsConverter` 가 만든 익명 객체가 7.0 의 인터페이스를 (5.0 시그니처 기준으로) 만족해야 한다. 만약 7.0 에서 `ReadListener` 에 새 추상 메서드가 추가되면 common 의 `ReadListenerConverter` 가 7.0 에서 동작 불가. 그때는 다음 중 선택:
  - **(a)** common 을 `common5`, `common7` 등 ABI 호환 단위로 분리 (자체 fork)
  - **(b)** common 의 jakarta 핀을 5.0 → 7.0 으로 올리되, 5.0 모듈에서 common 의 클래스가 5.0 인터페이스를 만족하지 못하므로 5.0 모듈은 별도 common5 로 fork
  - **(c)** 해당 컨버터를 common 에서 버전별 모듈로 downgrade

→ **현 단계에서 7.0 대비 추상화는 하지 않는다 (오버엔지니어링)**. 7.0 출시 시점에 평가.

### 8.3 javax 3.x 지원 시나리오

- 사용자가 javax-servlet 3.x 코드를 어댑팅하고 싶다고 가정. 4.0 → 3.x 는 어댑터 입장에서 *javax 측 의존* 만 다운그레이드 하는 것.
- 현 어댑터는 javax 측에 deprecated 메서드를 위임하는 곳이 많으므로 3.x 컴파일이 *추가로 깨질 수 있다*. 예: `Cookie.setComment` 는 3.x 에도 존재하므로 OK. `HttpServletRequest.isRequestedSessionIdFromUrl` 도 3.x 에 존재.
- **방법**: 모듈 ID 의 두 축(jakarta 버전 + javax 버전) 을 모두 인덱스로 삼는 모듈 매트릭스 가 필요해진다 — `servlet5-jx4`, `servlet5-jx3` ... 폭발적.
- **현실적 권장**: javax 측 의존은 **4.0 으로 핀**. 3.x 가 필요한 사용자에게는 *4.0 인터페이스의 부분집합* 이라는 점을 안내 (javax-servlet 3.x → 4.0 은 거의 추가만 됨).
- 만약 정말 3.x 가 필요해진다면, 그때 별도 fork 모듈을 만든다.

### 8.4 확장성 결론

- multi-module 토폴로지는 **새 jakarta 버전 추가에 직선적으로 비례**한다 (모듈 1개 추가).
- common 의 jakarta API 핀은 **새 버전이 ABI breaking 일 경우 재평가** 가 필요한 지점.
- javax 측 분기까지 지원하면 매트릭스가 폭발하므로, **javax 는 4.0 핀 고수** 가 합리적.

```groovy
jar {
    manifest {
        attributes 'Automatic-Module-Name': 'com.clipsoft.servlet.adapter.servlet5'
    }
}
```

- 향후 본격 JPMS 지원(module-info.java) 은 사용자 요구가 모이면 도입.

### 9.4 OSGi 환경 위험

- `Bundle-SymbolicName`, `Bundle-Version` 미설정 시 OSGi 환경에서 사용 불가. 일반 OSGi 컨테이너에 배포하지 않는다는 가정 하에 미지원 명시.
- 필요해지면 `org.dm.bundle` 또는 `biz.aQute.bnd.builder` Gradle 플러그인으로 OSGi metadata 추가.

### 9.5 fat-jar / shadow plugin 위험

- 사용자가 자신의 애플리케이션에서 본 어댑터를 fat-jar 로 패키징할 때:
  - 어댑터의 `compileOnly` 의존(`jakarta.servlet-api`) 은 fat-jar 에 포함되지 않음 — 안전.
  - 단 사용자가 `implementation 'jakarta.servlet:jakarta.servlet-api:5.0'` 같이 잘못 선언하면 jakarta API 가 fat-jar 에 들어가 컨테이너의 jakarta API 와 충돌. 사용자 측 실수.
- **메서드 시그니처 누락**: shadow plugin 의 `relocate` 기능으로 어댑터의 패키지명을 변경하면(`adapter.jakarta.servlet6` → `myproject.adapter.jakarta.servlet6`), `@Override` 가 깨질 수 있음 (`implements jakarta.servlet.http.HttpServletRequest` 는 그대로지만, 어댑터의 fully-qualified class 명만 바뀜). 영향 미미.

### 9.6 의존 누수 위험 (common ↔ servlet*)

- common 이 `compileOnly 'jakarta.servlet-api:5.0'` 로만 의존하므로, servlet6 모듈에서 common 을 사용할 때 jakarta 5.0 API jar 가 transitive 로 끼어들지 않는다. 단 IDE 에서 common 모듈을 따로 열 때는 5.0 API 가 보임.
- **검증 권장**: CI 의 `:servlet6:dependencies` 출력에서 jakarta-servlet-api:5.0 이 *없어야* 한다 (compileOnly 는 transitive 되지 않음).
