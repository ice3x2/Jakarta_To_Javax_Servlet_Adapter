# Servlet 6.0 + 6.1 모듈 통합 vs 분리 결정 연구

## 0. 연구 범위와 결론 요약

본 문서는 `Jakarta_To_Javax_Servlet_Adapter` 의 Servlet 6.0 / 6.1 지원을 **하나의 모듈로 통합**할지, **두 개의 모듈로 분리**(기존 `50.architecture.md` 권장안)할지 결정하기 위한 심층 조사다. 코드 변경은 일절 하지 않고, 의사결정 근거와 절충안만 다룬다.

### 사전 사실 재정리

- **5 → 6.0 은 파괴적 (Big-Bang 정리)** — 인터페이스에서 제거된 메서드 다수 (`HttpSessionContext` 인터페이스 통째 삭제, `encodeUrl/encodeRedirectUrl/setStatus(int,String)`, `HttpSession.getValue/putValue` 등). 단 `60.conversion-strategy.md §6.1.7` 에서 정리한 대로 `ServletRequest.getRequestId/getProtocolRequestId/getServletConnection` 3개 **신규 추상 메서드** 도 추가되어 어댑터에 구현 강제력이 생긴다.
- **6.0 → 6.1 은 증분 (파괴적 변경 0건)** — 새 시그니처 5종, 새 상태 상수 4종, 신규 deprecation 1종(`PushBuilder`). 어댑터가 implements 측에서 직접 override 가 강제되는 **단 하나의 신규 추상 메서드** 는 `HttpServletResponse.sendRedirect(String, int, boolean)` 뿐이다 (나머지 `sendRedirect(String, int)` 와 `sendRedirect(String, boolean)` 은 6.1 spec 상 인터페이스의 `default` 메서드이므로 override 강제 아님 — Tomcat 11 의 6.1 javadoc 으로 확인됨).
- **플랫폼 분기**: 5.0 = Java 8, 6.0 = Java 11, 6.1 = Java 17. 6.1 spec 자체가 "Java SE 17 or higher" 를 명시.
- **사실 확인 (jakarta-servlet-api:6.1.0 bytecode)**: Maven Central 의 6.1.0 POM 본문 접근이 직접 403 으로 막혔으나, spec 본문(`jakarta.ee/specifications/servlet/6.1`) 이 "Java SE 17 이상" 을 명시하고 Tomcat 11 의 javadoc 도 6.1 API 를 Java 17 baseline 으로 다룬다. **6.1.0 jar 의 클래스 파일은 Java 17 bytecode (major version 61) 로 봐도 무방** 하다고 결론짓는다 — 본 결정에 다른 가능성이 영향을 주는 지점이 없으므로 추가 검증 비용 대비 가치 낮음.

### 결론 (4개 옵션 중 권장)

| 옵션 | 평가 |
|---|---|
| A. **분리 유지 (servlet6 + servlet61)** — 50.architecture.md 권장 그대로 | **권장** |
| B. 통합 (servlet6 단일, jakarta 6.0 API + Java 11) | 매력적이나 6.1 사용자에게 `sendRedirect(loc, sc, clearBuffer)` 호출 시 `AbstractMethodError` 리스크 보유 — 차선책 |
| C. 통합 (servlet6 단일, jakarta 6.1 API + Java 17) | 6.0 사용자(Java 11) 가 사용 불가 — 부적합 |
| D. 조건부 통합 (servlet6 단일, Java 11, jakarta 6.0 compileOnly + 6.1 reflection 분기) | 복잡도 폭증, 어댑터의 본질에 어긋남 — 부적합 |

**최종 권장: 옵션 A (분리)**. 50.architecture.md 갱신 불필요. 단 권장에 따른 정당화 근거와 옵션 B 와의 비교를 본문에서 상술한다.

## 1. Q1. 정량 비교

### 1.1 비교 표

| 항목 | 통합 (servlet6 단일) | 분리 (servlet6 + servlet61) |
|---|---|---|
| 코드 사본 LOC (jakarta + javax + servletElementConverter, 모듈당) | **~3,225 LOC** × 1 = 3,225 | ~3,225 × 2 = **~6,450** (단 6.1 은 6.0 사본에서 단 1~2 메서드 추가만으로 만들어지므로 실질 *diff LOC* 는 ~10) |
| `ServletAdapter` 진입점 (80 LOC × N) | 80 × 1 = 80 | 80 × 2 = 160 |
| 빌드 모듈 수 | common + servlet5 + **servlet6** + bom = **4** | common + servlet5 + **servlet6** + **servlet61** + bom = **5** |
| CI 매트릭스 셀 수 (각 모듈 × JDK) | 5 (8) + 6 (11) = **2 JDK 라인** | 5 (8) + 6 (11) + 6.1 (17) = **3 JDK 라인** |
| jar 파일 수 (publish 대상) | servlet5, servlet6, bom = **3 (+sources/javadoc 6 jar)** | + servlet61 = **4 (+sources/javadoc 8 jar)** |
| Maven Central 게시 자동화 부담 | 모듈 1개 적음 (publish task 1개 적음) — 미미한 차이 | 모듈 1개 더 — Sonatype 게시 스크립트가 모듈을 loop 하는 구조면 추가 비용 없음 |
| 신규 jakarta 7 추가 시 작업량 | **불리** — 통합 라인을 다시 쪼개거나, 6.0~7 의 ABI 차이를 한 모듈에 누적 ⇒ 모듈이 점점 커짐 | **유리** — `servlet7` 모듈 1개 추가 (servlet61 사본 + 7.0 차이만 적용) |
| 패키지명 마이그레이션 비용 (사용자) | 단일 패키지 `adapter.jakarta.servlet6.*` — 6.0/6.1 사용자 모두 동일 import | 두 패키지 — 6.0 vs 6.1 사용자가 자기 모듈 import — 명확하나 인지 부담 |
| 어댑터 jar 의 `Cookie.setAttribute` 등 6.0+ 신규 API 노출 | 통합 시 jakarta 6.0 API 로 컴파일하면 동일 노출 가능 (5→6 신규 API 는 모두 6.0 에 있음) | 동일 |
| 어댑터 jar 의 `sendRedirect(String, int, boolean)` 등 6.1 신규 API 노출 | **불가** — 6.0 API 로 컴파일된 어댑터 클래스에는 6.1 인터페이스에서 추가된 추상 메서드 override 가 없음 | **가능** — servlet61 모듈이 6.1 API 로 빌드, 명시적으로 override |

### 1.2 정량 차이의 실제 크기

- **LOC 비용**: 분리가 통합 대비 약 **3,300 LOC 더 들어간다** (servlet61 모듈 한 벌). 그러나 6.1 모듈은 6.0 모듈의 *사본 + 단 1~2 메서드 추가*. git diff 의 95% 이상이 사본이며, 의미 있는 *유지보수 노력* 은 1~2 메서드.
- **CI 셀**: 매트릭스 한 줄 차이는 CI 시간에 거의 영향이 없다 (각 모듈은 독립적으로 1분 미만 빌드). Gradle Toolchain 이 JDK 17 자동 다운로드를 처리하므로 CI 환경 자체에 별도 설치도 불필요.
- **사용자 의존 표현**: 분리 시 `implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet6:1.0'` vs `implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet61:1.0'`. 사용자가 한 줄 더 길게 쓴다고 비용은 사실상 0.

**정량 비교에서 분리 vs 통합의 비용 차는 매우 작다** — 결정 요인은 정성적(아래 Q2~Q4) 측면에 있다.

## 2. Q2. ClassLoader / 양 버전 동시 사용 시나리오

### 2.1 어댑터를 두 컨테이너에 임베드하는 시나리오

본 어댑터의 *변환 기능* 은 두 jakarta 버전이 한 JVM 안에 임베드되는 시나리오를 자연스럽게 끌어들인다 — 예: 마이그레이션 중인 게이트웨이가 Tomcat 10.1 과 Tomcat 11 양쪽 서블릿 객체를 한 호스트에서 변환.

이때 클래스로더 격리는 **전제**다 (JVM 은 동일 FQCN `jakarta.servlet.http.HttpServletResponse` 클래스를 한 클래스로더에서 한 번만 로드). 두 jakarta-servlet-api jar 가 서로 다른 ClassLoader 에 로드되고, 어댑터 jar 도 각 ClassLoader 에 별도로 로드된다.

### 2.2 통합 시 동작 분석

가정: `servlet6` 통합 모듈이 jakarta 6.0 API 로 compileOnly 빌드 (옵션 B).

| ClassLoader | 로드된 jakarta API | 로드된 어댑터 jar | 어댑터가 implements 한 인터페이스 | 결과 |
|---|---|---|---|---|
| CL_60 | jakarta-servlet-api **6.0** | servlet6.jar | jakarta 6.0 `HttpServletResponse` | 정상. 6.0 의 모든 추상 메서드 구현 보유 |
| CL_61 | jakarta-servlet-api **6.1** | servlet6.jar | jakarta 6.1 `HttpServletResponse` (런타임에 6.1 시그니처로 다시 resolve) | **위험**. 어댑터 클래스의 바이트코드는 6.0 인터페이스 기준이라 `sendRedirect(String, int, boolean)` 메서드 미보유 → 호출 시 `AbstractMethodError` |

핵심: 어댑터의 클래스 파일(`adapter.jakarta.servlet6.http.HttpServletResponse.class`) 은 `InnerClasses`·`MethodRef` 등의 attribute 에 jakarta 인터페이스를 *심볼로* 참조한다. 컴파일 시 6.0 인터페이스로 link 되었지만, 런타임 ClassLoader 가 6.1 인터페이스를 제공하면 그 클래스의 *vtable 구성* 은 다음과 같이 결정된다:

1. JVM 이 어댑터 클래스를 로드.
2. `implements jakarta.servlet.http.HttpServletResponse` 의 인터페이스 — 같은 ClassLoader 의 jakarta 6.1 인터페이스로 resolve.
3. 6.1 인터페이스의 모든 추상 메서드를 어댑터가 구현하는지 검증. `sendRedirect(String, int, boolean)` 의 구현 메서드를 어댑터 클래스의 메서드 셋에서 찾는다.
4. 없음 → JVM 은 클래스 로드 자체는 *통과*시키되, 해당 추상 메서드가 호출될 때 `AbstractMethodError` 를 throw.

(어떤 JVM 은 클래스 로딩 시점에 verifier 가 더 엄격하게 처리해서 `IncompatibleClassChangeError` 또는 `AbstractMethodError` 를 즉시 발생시키기도 한다.)

**즉 옵션 B (통합 + jakarta 6.0 컴파일) 는 6.1 환경에서 어댑터 사용자가 `sendRedirect(String, int, boolean)` 를 호출하는 순간 깨진다.** 사용자가 이 메서드를 호출하지 않는 한 동작은 한다. 그러나 어댑터의 가치 제안이 "양방향 변환" 인데, *6.1 의 신규 시그니처를 호출할 수 없다는 한계* 는 사용자 경험에 큰 흠집이다.

(반대로 옵션 C — 통합 + jakarta 6.1 컴파일 — 의 경우, 어댑터 클래스 바이트코드가 6.1 인터페이스 의존이고, 6.0 환경에 로드되면 6.0 인터페이스에 *없는* 메서드를 override 하려 시도한다. 6.0 인터페이스에 메서드가 없으니 단순히 사용되지 않을 뿐이라 `NoSuchMethodError` 가 곧장 나지는 않지만, 어댑터 클래스의 일부 코드가 6.1 의 새 *추상 메서드* 를 호출한다면 그 시점에 `NoSuchMethodError` 가 난다. 본 어댑터는 위임 일색이므로 호출 자체는 잘 발생하지 않으나, **Java 17 컴파일 → Java 11 런타임 호환은 불가능** — JVM 의 class file major version mismatch 로 `UnsupportedClassVersionError` 가 즉시 throw 된다. 이게 옵션 C 의 즉시 실격 사유다.)

### 2.3 분리 시 동작 분석

| ClassLoader | 로드된 jakarta API | 로드된 어댑터 jar | 결과 |
|---|---|---|---|
| CL_60 | jakarta-servlet-api 6.0 | **servlet6.jar** (6.0 컴파일) | 정상 |
| CL_61 | jakarta-servlet-api 6.1 | **servlet61.jar** (6.1 컴파일) | 정상. `sendRedirect(loc, sc, clearBuffer)` override 보유 |

각 ClassLoader 가 자기 jakarta 버전에 맞는 어댑터 jar 를 로드. 깨끗.

### 2.4 결론

**ClassLoader 양 버전 동시 사용 시나리오는 분리 옵션이 명백히 우세**. 통합 옵션 B 는 6.1 환경의 어댑터 사용자에게 `AbstractMethodError` 잠재 위험을 남긴다.

## 3. Q3. 통합 시 6.1 신규 시그니처 노출 정책

### 3.1 옵션 (a): servlet6 모듈을 jakarta 6.0 API 로 compileOnly 빌드

| 항목 | 동작 |
|---|---|
| 빌드 타임 | jakarta 6.0 API 가 classpath. 어댑터의 `adapter.jakarta.servlet6.http.HttpServletResponse` 는 6.0 인터페이스를 implements. `encodeUrl`·`getSessionContext` 등 5.0 잔존 메서드는 제거됨. `sendRedirect(loc, sc, clearBuffer)` 는 어댑터에 정의 *없음* (6.0 인터페이스에 없으므로) |
| 6.0 컨테이너 런타임 | 정상. 어댑터의 메서드 셋이 jakarta 6.0 인터페이스의 추상 메서드 셋을 정확히 만족 |
| 6.1 컨테이너 런타임 | jakarta 6.1 의 `HttpServletResponse` 는 새 추상 메서드 `sendRedirect(loc, sc, clearBuffer)` 보유. 어댑터 클래스는 이 메서드를 구현하지 않음. 사용자가 이 메서드를 호출하면 **`AbstractMethodError`** (메서드 자체가 어댑터 클래스의 method table 에 없음) |
| 6.1 의 default 메서드 (`sendRedirect(loc, sc)`, `sendRedirect(loc, boolean)`) | 6.1 인터페이스가 default 구현을 제공. default 본체가 `sendRedirect(loc, sc, clearBuffer)` 를 호출하도록 설계됨. 따라서 default 가 호출되어도 결국 abstract `sendRedirect(loc, sc, clearBuffer)` 에 도달 → 같은 `AbstractMethodError` |

→ **6.1 환경에서 옵션 (a) 의 어댑터는 새 redirect 오버로드를 사실상 사용 불가**. 사용자가 이 메서드를 호출하지 않으면 평온하지만, *언제 호출할지 어댑터가 통제 불가*.

### 3.2 옵션 (b): servlet6 모듈을 jakarta 6.1 API 로 compileOnly 빌드

| 항목 | 동작 |
|---|---|
| 빌드 타임 | jakarta 6.1 API 가 classpath. 어댑터는 `sendRedirect(loc, sc, clearBuffer)` 를 override 가능. **하지만 Java 17 컴파일 필요** (6.1 spec 이 Java 17 baseline) |
| Java 17 컴파일 → Java 11 런타임 | `UnsupportedClassVersionError` — major 61 class file 을 JDK 11 (major 55) JVM 이 load 거부 |
| Java 17 컴파일 → Java 17 런타임 + jakarta 6.0 컨테이너 | 어댑터 클래스 파일 자체는 로드된다 (major 61 → JDK 17 OK). 단 어댑터가 6.1 의 *새 추상 메서드* `sendRedirect(loc, sc, clearBuffer)` 를 override 한 메서드 본체가 있다. 6.0 인터페이스에는 이 메서드가 없으므로 **호출 경로가 없을 뿐**, 어댑터 클래스의 다른 메서드는 정상 동작. → **6.0 인터페이스를 통한 호출은 깨지지 않음**. 단 사용자가 6.0 컨테이너에서 어댑터의 6.1-only 메서드를 호출하면(예: `Cookie.getAttribute` 가 어댑터 내부에서 6.1 메서드를 호출하면) `NoSuchMethodError`. 본 어댑터는 위임 위주라 그런 *내부 호출* 이 거의 없음 — 그래도 옵션 (b) 는 **6.0 환경 사용자가 Java 11 인 한 사용 불가**라는 결정적 한계 보유 |

→ **옵션 (b) 는 Java 17 환경에서만 사용 가능**. 6.0 사용자(Java 11) 를 컷오프하면 통합의 의미가 사라진다 ("6.0 + 6.1 통합" 이 아니라 단지 "6.1 라인 단독" 이 됨).

### 3.3 옵션 (c): 6.0 인터페이스의 메서드만 override + 6.1 신규 추상 메서드는 reflection/MethodHandle 로 우회

기본 구조: jakarta 6.0 API 로 컴파일. 단 `adapter.jakarta.servlet6.http.HttpServletResponse` 클래스가 *런타임에 6.1 인터페이스로 로드되면* 추상 메서드 미구현 상태가 된다는 점을 우회하기 위해, **어댑터 클래스가 6.1 의 `sendRedirect(loc, sc, clearBuffer)` 시그니처를 가진 메서드를 미리 정의** 한다. 컴파일은 6.0 API 로 하므로 `@Override` 어노테이션은 못 쓰지만, 메서드 시그니처를 정확히 일치시키면 vtable 에 등재된다.

```java
// 6.0 API 로 컴파일되는 어댑터 클래스
public class HttpServletResponse implements jakarta.servlet.http.HttpServletResponse {
    private final javax.servlet.http.HttpServletResponse origin;

    // 6.1 신규 — @Override 없음 (6.0 API 컴파일이라 6.1 인터페이스를 모름). 시그니처만 정확히 일치
    public void sendRedirect(String location, int sc, boolean clearBuffer) throws java.io.IOException {
        origin.setStatus(sc);
        origin.setHeader("Location", location);
        if (clearBuffer) origin.resetBuffer();
        origin.flushBuffer();
    }
    // ... 나머지 6.0 메서드 위임
}
```

| 항목 | 동작 |
|---|---|
| 6.0 컨테이너 | 위 메서드가 단순 *추가 메서드* 일 뿐, 6.0 인터페이스에는 없음. 호출 경로가 없으므로 무해 |
| 6.1 컨테이너 | 6.1 인터페이스의 `sendRedirect(loc, sc, clearBuffer)` 추상 메서드를 위 메서드가 (시그니처 일치로) 구현하는 것으로 JVM 이 인식. 정상 동작 |
| 빌드 검증 | 컴파일 단계가 6.1 인터페이스를 모르므로 *시그니처 오타* 가 발생해도 컴파일은 통과. CI 에서 6.1 환경 통합 테스트로만 잡힘 — **회귀 위험 높음** |

추가 복잡도:
- `SC_PERMANENT_REDIRECT` 등 6.1 신 상수는 컴파일 타임에 모르므로 사용자가 직접 `308` literal 을 써야 한다 (어댑터가 상수를 노출 못 함).
- `isSensitiveHeader` 같은 6.1 신규 default 메서드를 어댑터에 정의하려면 같은 패턴 반복.
- jakarta 6.1 의 `PushBuilder` deprecation 등 미세한 차이는 noted 만 가능.

이 옵션은 *기술적으로 가능하나*:
1. 컴파일 안전망 상실 (시그니처 오타 회귀 위험)
2. 새 상수 노출 불가
3. 미래 6.2 / 7 추가 시 같은 패턴을 매번 반복 — 코드 복잡도 누적
4. 본 어댑터의 "단순 Decorator 위임" 본질에 정면 어긋남

→ **부적합. 옵션 D 와 사실상 등가** (D 는 reflection 까지 동원).

### 3.4 옵션 (d): jakarta 6.0 compileOnly + 6.1 reflection 분기

`sendRedirect(loc, sc, clearBuffer)` 를 어댑터에 정의하지 않되, 어댑터 클래스 로드 시 6.1 인터페이스가 감지되면 ASM/ByteBuddy 등으로 동적 subclass 를 만들어 메서드 추가.

| 항목 | 동작 |
|---|---|
| 복잡도 | ByteBuddy 의존 추가. 어댑터의 *정적 위임 본질* 이 *동적 클래스 합성 시스템* 으로 변질. 디버깅·스택트레이스 가독성 저하. JIT/AOT 최적화 저해 |
| 사용자 영향 | shadow plugin 으로 패키지 relocate 하면 ByteBuddy 가 합성한 클래스 이름이 흔들릴 수 있음. ClassLoader 격리 시나리오에서 ByteBuddy 가 어떤 ClassLoader 에 합성 클래스를 정의하느냐가 새 문제 |

→ **본 어댑터에는 과도. 부적합**.

### 3.5 `AbstractMethodError` vs `NoSuchMethodError` 의 발생 조건 정확화

| 에러 | 발생 조건 | 본 케이스 |
|---|---|---|
| **`AbstractMethodError`** | 클래스가 *implements 한 인터페이스* 의 추상 메서드를 구현하지 않은 상태로 클래스 로드는 통과했으나, 그 추상 메서드가 호출될 때 throw | 옵션 B + 6.1 환경 + 사용자가 `sendRedirect(loc, sc, clearBuffer)` 호출 시 발생 |
| **`NoSuchMethodError`** | *호출자* 가 어떤 메서드를 호출하려 하나, 호출 대상 클래스에 그 메서드가 더 이상 없을 때 (예: 호출자가 컴파일된 시점과 런타임 클래스의 메서드 셋이 다름) | 옵션 C (6.1 컴파일 → 6.0 런타임) 에서 *만약* 어댑터 내부 코드가 6.1-only 시그니처를 호출했다면. 본 어댑터는 외부에서 들어오는 호출만 위임하므로 발생 시나리오 좁음 |
| **`UnsupportedClassVersionError`** | class file major version 이 현재 JVM 보다 높을 때 | 옵션 C (Java 17 컴파일) + JDK 11 런타임. 클래스 로드 자체가 실패 |

본 결정의 가장 큰 리스크는 옵션 B 의 `AbstractMethodError`. 사용자가 어댑터를 통해 6.1 신 redirect 오버로드를 호출하는 시나리오는 *Spring MVC 의 `DefaultRedirectStrategy.sendRedirect`* 등 프레임워크가 이미 6.1 신 API 로 마이그레이션한 경우 발생할 수 있다 — 즉 잠재적이지만 실재.

## 4. Q4. Java 17 요구의 영향

### 4.1 사실

- **jakarta-servlet-api:6.1.0** spec 의 baseline 은 **Java SE 17**.
- 어댑터의 servlet61 모듈이 6.1 API 를 implements 하려면 컴파일·런타임 모두 Java 17 필요 (단순히 API 의존이 17 이상 클래스를 사용하느냐 별개로, 6.1 spec 자체가 "이 API 는 Java 17 위에서만 동작 보장" 을 선언).
- Servlet 6.0 (Tomcat 10.1 의 baseline) 은 Java SE 11.

### 4.2 통합 시 Java 타깃 결정의 trilemma

- **Java 11 타깃 (옵션 B)**: 6.0 환경 (Java 11) 사용자 가능, 6.1 환경 (Java 17) 사용자도 forward-compatible 로 가능 (Java 17 JVM 이 major 55 class 를 로드). 단 6.1 *추상 메서드* 미구현 → `AbstractMethodError` 위험 (§Q3 §3.1).
- **Java 17 타깃 (옵션 C)**: 6.1 환경 OK. 6.0 환경 (Java 11) 사용자는 클래스 로드 자체 실패. 사실상 servlet61 단독.
- **하이브리드 (Multi-Release JAR)**: `META-INF/versions/17/` 하위에 6.1-aware 클래스를 두고 메인 트리에 6.0-aware 클래스를 둠.
  - MRJAR 는 *JVM 버전* 에 따라 분기. *jakarta API 버전* 에 따라 분기 아님.
  - JDK 17 JVM 위에서 jakarta 6.0 컨테이너를 돌리는 경우, MRJAR 는 17 버전 클래스를 로드 (6.1-aware) → 6.0 인터페이스를 implements 한 클래스가 6.1-only 메서드를 갖고 있어 무해하지만, *6.1 신 default 메서드를 호출* 하려고 시도하면 6.0 인터페이스에 default 가 없으므로 `NoSuchMethodError`. 일관성 약함.
  - 결론: MRJAR 는 본 케이스의 핵심 분기축(=jakarta API 메이저) 과 직교가 맞지 않아 **부적합** (이미 `40.support-strategy.md §4.2 옵션 A` 에서도 부적합으로 정리됨).

### 4.3 jakarta-servlet-api:6.1.0 jar 자체가 Java 17 로 빌드되었는지

- spec 본문이 "Java SE 17 or higher" 를 baseline 으로 선언.
- Tomcat 11 release note 가 "JDK 17+ required".
- 6.1 javadoc 의 메서드 시그니처 (e.g., `sendRedirect(String, int, boolean)`) 는 sealed 등 17-only language feature 를 사용하지 않음. 즉 *기술적으로는* 11 bytecode 로도 컴파일 가능했을 것. 그러나 spec 이 baseline 을 17 로 정한 이상, 어댑터의 servlet61 모듈도 17 baseline 을 따르는 것이 spec 준수.
- 본 결정에서 핵심은 **사용자 환경**. 6.1 사용자는 Tomcat 11 을 쓰므로 Java 17 환경이 보장됨. 어댑터의 servlet61 jar 가 major 61 (Java 17) bytecode 라도 사용자에게 부담 없음.

### 4.4 통합 시 Java 타깃 결정 결과

- 옵션 B (Java 11 타깃) 가 *기술적으로는 가장 호환성 넓다* 는 환상.
- 그러나 6.1 의 `sendRedirect(loc, sc, clearBuffer)` 추상 메서드를 어떻게 처리해도 한 가지 비용을 치러야 함:
  - 미구현 → 옵션 B 의 `AbstractMethodError` 위험
  - 구현 → 옵션 (c) 의 안전망 상실 + 복잡도

→ **Java 17 baseline 으로 servlet61 분리 모듈을 두는 분리안이 가장 깨끗**. 분리안은 servlet6 모듈을 Java 11 타깃으로, servlet61 모듈을 Java 17 타깃으로 둠으로써 두 환경 사용자 모두에게 최적 jar 를 제공.

## 5. Q5. 사용자 베이스 추정 (2026년 5월 시점)

### 5.1 Tomcat 10.1 (Servlet 6.0) vs Tomcat 11 (Servlet 6.1) 채택 추이

웹 검색으로 확인된 사실:

- **Tomcat 11.0** GA: 2024-10. 첫 stable (11.0.6): 2025-04. 최신: 11.0.22 (2026-05).
- **Tomcat 10.1** GA: 2022-09. 2026-05 시점에도 활발한 패치 진행 중. 두 라인 모두 *현행 stable*.
- **Apache Tomcat "Which Version Do I Want"** 표는 현재 (2026-05) 시점에 10.1.x 와 11.0.x 양쪽을 *current stable* 로 명시. 즉 LTS 적 위상이 비슷.
- **70% of Java developers use Tomcat** (Perforce JRebel 2025 보고서).
- 11.0 의 첫 stable (2025-04) 출시 후 1년이 지난 2026-05 시점. 신규 그린필드 프로젝트는 11.0 으로 시작하는 추세, 기존 프로덕션은 10.1 유지가 흔함.

### 5.2 Spring Boot / Framework 의 jakarta-servlet 의존

- Spring Boot 3.x → Jakarta EE 9/10 baseline → Servlet 5.0/6.0 의존.
- Spring Boot 3.4 (2024-11 출시), 3.5 (2025-05), 3.6 (2025-11) 까지의 라인은 servlet 6.0 까지를 권장.
- Spring Boot 4.0 (2025-Q4 alpha, 2026-Q2 GA) 부터 **Servlet 6.1 호환 컨테이너 권장**. Java 17 baseline.
- 즉 2026-05 현재, Spring Boot 3.x 사용자는 servlet 6.0 의존이 다수. Spring Boot 4.x 로 마이그레이션한 신규 프로젝트는 servlet 6.1.
- 본 어댑터의 주 고객층은 *javax 4.0 레거시 코드를 jakarta 환경으로 가져오려는* 마이그레이션 사용자 — 이들은 Tomcat 10.1 (6.0) 으로 우선 마이그레이션 후, Tomcat 11 (6.1) 로 단계적 이행하는 경향. **양쪽 사용자 동시 존재**.

### 5.3 향후 1~2년 전망

- **2026~2027**: 6.0 사용자 베이스 여전히 다수. 6.1 사용자가 증가하나 6.0 을 빠르게 대체하지는 못함. 두 라인이 공존.
- **2027~2028**: Tomcat 10.1 EOL 가능성 등장. Spring Boot 4.x 가 mainstream 이 되면 6.0 → 6.1 마이그레이션이 가속. 단 본 어댑터의 고객은 *마이그레이션이 느린 레거시 기반 조직* 이라는 점에서 6.0 라인이 더 오래 갈 가능성.

### 5.4 사용자 베이스 추정의 결정 영향

- **6.0 사용자가 곧 사라지지 않음** → servlet61 모듈을 별도로 제공하는 가치가 *살아 있다*. 만약 6.0 이 1년 안에 사라질 추세였다면 통합이 더 매력적이지만, 향후 2~3년 공존이 거의 확실.
- **6.1 신기능 (`sendRedirect` 오버로드, 새 상태 상수) 의 어댑터 노출 가치** — Spring MVC 등 6.1-aware 프레임워크가 직접 호출하므로 노출은 가치가 있다. 옵션 B 의 `AbstractMethodError` 잠재 위험을 회피하려면 분리가 안전.

## 6. Q6. 향후 확장성

### 6.1 6.2 / 7.0 출시 시나리오

| 출시 | 통합 라인의 비용 | 분리 라인의 비용 |
|---|---|---|
| 6.2 (증분, 6.1 + 알파) | 현재 servlet6 (통합) 에 6.1+6.2 신규 시그니처 누적. 어댑터 클래스가 점점 비대해지며 6.0 호환을 유지하려면 옵션 (c) 의 *static method 추가* 패턴이 반복됨 | servlet62 모듈 신설 (servlet61 사본 + 6.1→6.2 차이). 1주 미만 |
| 7.0 (메이저 정리) | 통합 라인 폐기 + 라인 재분리 — 이 시점에 분리해야 하므로 통합의 임시 이득이 소거됨 | servlet7 모듈 신설. 분리 라인은 일정 비용 직선 누적 |

### 6.2 통합 라인이 한 번 정립되면 6.2 도 같은 모듈에 합칠 수 있는가?

가능. 그러나 그 시점에 servlet6 모듈은:
- 6.0 추상 메서드 셋 구현
- 6.1 추가 추상 메서드 (시그니처 일치로 vtable 등재) — `sendRedirect(loc, sc, clearBuffer)`
- 6.2 추가 (가상) 추상 메서드 — 더 추가
- 6.1 신 default 메서드의 *signature-only* 정의 — 추가
- 6.2 신 default 메서드의 *signature-only* 정의 — 추가

→ 어댑터 클래스가 *어떤 인터페이스를 implements 하는지* 가 컴파일 타임에 6.0 인데, 런타임에 6.2 까지 만족하도록 메서드를 모두 미리 정의해 두는 *지속적인 흩뿌리기*가 누적된다. 본 어댑터의 단순함이 사라진다.

**분리 라인은 모듈 1개를 깔끔히 추가**하는 패턴이라 누적 부담이 직선적이고 명료.

### 6.3 결론

- 통합 라인은 *현재 시점에 6.0/6.1 통합 비용이 작아 보이지만*, 미래 라인 추가 시 비용이 *non-linear* 로 증가.
- 분리 라인은 *현재 시점에 servlet61 추가 비용 ~3,300 LOC 사본*이지만, 미래에도 직선적.

50.architecture.md §8.1 의 6.2 추가 시나리오 분석과도 일관: "servlet62 모듈 신설" 패턴.

## 7. Q7. 사용자 측 의존 표현

### 7.1 통합 시

```groovy
implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet6:1.0.0'
```

한 줄로 6.0/6.1 모두 커버 (옵션 B 라면 6.1 의 `sendRedirect(loc, sc, clearBuffer)` 호출 시 깨짐 위험을 README 로 안내). 단순함.

### 7.2 분리 시

```groovy
// 6.0 환경 (Tomcat 10.1)
implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet6:1.0.0'

// 6.1 환경 (Tomcat 11)
implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet61:1.0.0'
```

사용자가 자기 환경의 jakarta 메이저를 알고 모듈 선택. 명확하나 인지 부담 있음.

### 7.3 BOM 사용 시

```groovy
// 통합 라인 BOM
dependencies {
    implementation platform('com.clipsoft:jakarta-to-javax-servlet-adapter-bom:1.0.0')
    implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet6'
}

// 분리 라인 BOM
dependencies {
    implementation platform('com.clipsoft:jakarta-to-javax-servlet-adapter-bom:1.0.0')
    implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet6'   // 6.0
    // 또는
    implementation 'com.clipsoft:jakarta-to-javax-servlet-adapter-servlet61'  // 6.1
}
```

BOM 사용 시 version 명시 비용은 양쪽 동일 (BOM 이 해결). artifact 명만 다름.

### 7.4 어느 쪽이 더 자연스러운가

- **단순함 측면**: 통합 우세 — "내가 servlet 6.x 쓰면 servlet6 모듈" 한 줄.
- **명확성 측면**: 분리 우세 — "내가 6.0 환경이면 servlet6, 6.1 환경이면 servlet61" 직관적.
- **사용자 실수 방지**: 분리 우세 — 통합은 옵션 B 의 잠재적 `AbstractMethodError` 가 사용자에게 잘 안내되지 않으면 production 에서 폭발할 수 있음. 분리는 *자기 환경의 jakarta 메이저* 를 명시적으로 선택하게 강제하므로 안전.
- **마이그레이션 가이드 가독성**: 분리 우세 — 6.0 → 6.1 마이그레이션 시 사용자는 *모듈 의존만 servlet6 → servlet61 로 바꾸면* 충분. 통합이면 "잘 안 깨지는지 직접 확인" 부담.

→ **결론: BOM 도입 전제 시 두 라인 모두 깔끔. BOM 없으면 분리가 안전성에서 우세**.

## 8. Q8. 어댑터의 본질에 비추어

### 8.1 어댑터의 본질

본 어댑터는 *Decorator 위주의 위임 어댑터*. 6.0 → 6.1 신규 시그니처가 어댑터에 큰 변화를 요구하지 않는다:

- `sendRedirect(loc, sc)`, `sendRedirect(loc, boolean)` — 6.1 default 메서드 (어댑터 측 override 강제 없음)
- `sendRedirect(loc, sc, clearBuffer)` — 6.1 abstract 메서드 (override **강제**)
- `SC_PERMANENT_REDIRECT (308)` 등 상수 — 상수일 뿐 implements 영향 없음 (어댑터의 다른 메서드가 사용자에게 노출됨)
- `HttpServlet.isSensitiveHeader` — 어댑터가 `HttpServlet` 을 직접 implements 하지 않으므로 무영향
- `PushBuilder` deprecation — *호출 가능 여부* 와 별개. 어댑터는 위임만 하므로 자유

→ **통합의 코드 비용은 실제로 최소**. servlet61 모듈을 분리해도 servlet6 모듈과 *diff 가 1~2 메서드뿐*. 코드 비용만 따지면 통합이 우세.

### 8.2 분리의 가치는 코드 비용이 아닌 다른 축

| 가치 | 설명 |
|---|---|
| **artifact 명명의 명확성** | 사용자가 자기 jakarta 버전을 알기 쉬움. `-servlet61` 이라는 artifact 명이 "이 jar 는 6.1 환경 전용" 을 자명히 전달 |
| **Java 17 요구 격리** | 6.1 spec 의 Java 17 baseline 을 명시적으로 격리. 6.0 사용자가 Java 11 환경에서도 사용 가능 |
| **6.1 신규 시그니처 first-class 노출** | servlet61 모듈이 6.1 인터페이스를 명시적으로 implements 하므로 모든 신규 시그니처가 안전하게 동작. `AbstractMethodError` 잠재 위험 0 |
| **확장성 청사진의 일관성** | 50.architecture.md 가 정립한 "1 모듈 = 1 jakarta 메이저" 청사진을 유지. 6.2 / 7 등 미래 추가 시 모순 없음 |

→ **분리의 가치는 정성적(명확성, 안전성, 청사진 일관성)에 집중**. 통합의 가치는 정량적(LOC, 모듈 수). 본 어댑터의 가치 제안이 *변환의 신뢰성*이므로 정성적 가치가 우선.

## 9. Q9. 최종 권장

### 9.1 결정

**옵션 A. 분리 유지 (servlet6 + servlet61)** — 50.architecture.md 의 권장안 그대로.

### 9.2 권장안의 장점 (정량 + 정성)

| 축 | 내용 |
|---|---|
| **정량** | 코드 사본 1개 추가 (~3,300 LOC, 단 실질 diff 는 ~10 LOC). 빌드 모듈 1개 추가. CI JDK 라인 1개 추가 (Toolchain 으로 자동화). 게시 jar 1개 추가 |
| **정성: 안전성** | `AbstractMethodError` 잠재 위험 0. 6.1 신규 추상 메서드 `sendRedirect(loc, sc, clearBuffer)` 가 모듈 내에서 명시적으로 override |
| **정성: 명확성** | artifact 명 (`-servlet6` vs `-servlet61`) 이 사용자 환경을 자명히 전달. import 시 패키지 (`adapter.jakarta.servlet6` vs `adapter.jakarta.servlet61`) 도 동일 |
| **정성: 확장성** | "1 모듈 = 1 jakarta 메이저" 청사진 유지. 6.2 / 7 / 8 추가 시 패턴 일관 |
| **정성: 청사진 일관성** | 50.architecture.md, 60.conversion-strategy.md (방향별 폴백 정책이 메이저 단위로 정리됨), 70.testing-strategy.md (CI 매트릭스가 메이저별 셀로 구성) 모두와 정합 |

### 9.3 권장안의 단점 (정량 + 정성)

| 축 | 내용 |
|---|---|
| **정량** | 코드 사본 비용. CI 빌드 시간 약간 증가 (모듈 1개 추가). Maven Central 게시 모듈 1개 추가 |
| **정성: 단순성** | 사용자가 자기 jakarta 메이저를 알아야 모듈 선택 가능. BOM 없으면 사용자 인지 부담 |
| **정성: 코드 중복** | servlet6 와 servlet61 모듈 간 95% 사본. git diff 가독성·search 노이즈 증가 |

### 9.4 리스크 완화책

1. **코드 중복 완화**: `common` 모듈이 ABI 면역 부분을 흡수 (50.architecture.md §2.2). servlet6 와 servlet61 사이 *유지보수 동기화 의무* 는 차이 부분(~10 LOC) 만 대상. 공통 변경은 common 에 일원화.
2. **사용자 인지 부담 완화**: BOM 모듈 게시 (50.architecture.md §5.7). README 첫 화면에 "내가 Tomcat 10.1 인가 11 인가?" 라는 결정 트리 한 줄 추가.
3. **CI 부담 완화**: Gradle Toolchain 으로 JDK 11/17 자동 다운로드. 단일 JDK 17 환경의 CI 머신에서 전체 빌드 가능.
4. **artifact 명 충돌 회피**: 이미 50.architecture.md §3.2 가 `adapter.jakarta.servlet6` vs `adapter.jakarta.servlet61` 패키지 분리를 권장. 양 모듈을 한 ClassLoader 에 동시 의존하더라도 FQCN 충돌 없음.
5. **사용자 마이그레이션 path**: 6.0 → 6.1 환경 이행 시 사용자는 단지 `-servlet6` 의존을 `-servlet61` 로 교체 + `adapter.jakarta.servlet6.*` import 를 `adapter.jakarta.servlet61.*` 로 교체. IDE 의 find-and-replace 1분.

### 9.5 사용자 영향

#### 호환성 매트릭스 (분리 라인 1.0 시점)

| 사용자 환경 | 권장 모듈 | Java | jakarta API |
|---|---|---|---|
| Tomcat 9 (javax 4) — 어댑터를 javax→jakarta 방향으로만 쓸 경우 | (어댑터 사용 안 함 — 어댑터는 jakarta-servlet 컨테이너용) | — | — |
| Tomcat 10.0 (jakarta 5.0) | `-servlet5` | 8 이상 | jakarta 5.0 |
| Tomcat 10.1 (jakarta 6.0) | `-servlet6` | 11 이상 | jakarta 6.0 |
| Tomcat 11 (jakarta 6.1) | `-servlet61` | 17 이상 | jakarta 6.1 |
| 두 환경 동시 (ClassLoader 격리 전제) | 두 모듈 동시 의존 | 각 ClassLoader 에 맞게 | 각 ClassLoader 에 맞게 |

#### 마이그레이션 가이드 (6.0 → 6.1)

1. Tomcat 11 로 환경 이행.
2. JDK 11 → JDK 17 로 빌드 환경 변경.
3. Maven/Gradle 의존을 `-servlet6` → `-servlet61` 로 교체.
4. import 일괄 변환: `adapter.jakarta.servlet6` → `adapter.jakarta.servlet61` (IDE find-and-replace).
5. (선택) 6.1 신기능 (`sendRedirect(loc, sc, clearBuffer)`, `SC_PERMANENT_REDIRECT` 등) 사용 코드 도입.

## 10. Q10. 결정에 따른 50.architecture.md 갱신 사항

### 10.1 갱신 요약

**갱신 불필요**. 50.architecture.md §0 의 권장 토폴로지(`common/servlet5/servlet6/servlet61/bom`) 가 본 결정의 결과(=분리 유지)와 일치한다.

### 10.2 부수적 검토 — 50.architecture.md §10.4 의 "사용자 결정 필요" 항목 처리

50.architecture.md §10.4 "servlet 6.0 + 6.1 통합 가능성" 항목은 본 보고서로 **"분리 유지" 결정완료** 로 표기 가능. 다음과 같이 마무리 가능:

```markdown
### 10.4 servlet 6.0 + 6.1 통합 가능성

- 40.support-strategy.md:147 에서 "단일 source-set 으로 6.0/6.1 양쪽을 커버하는 것도 검토 가치가 있다" 고 함.
- 통합하면 모듈 1개 (`servlet6`) 가 6.0+6.1 양쪽 사용자를 커버. 단 6.1 신 시그니처 (`sendRedirect` 오버로드) 노출은 못 함.
- **결정 (55.module-split-decision.md)**: 분리 유지. `AbstractMethodError` 회피, 청사진 일관성, 6.1 신 시그니처 first-class 노출이 통합의 LOC 절감보다 가치 큼.
```

(50.architecture.md 의 다른 섹션은 분리 권고가 이미 일관되어 있으므로 추가 갱신 없음.)

### 10.3 60.conversion-strategy.md 와의 정합성

60.conversion-strategy.md §6.2.2 의 폴백 정책 표에 `sendRedirect` 오버로드 3종을 모두 다룬 행이 있다. 분리 라인에서 이 정책은 servlet61 모듈에 한정해서 적용됨 — 별도 갱신 불필요.

### 10.4 70.testing-strategy.md 와의 정합성

70.testing-strategy.md 의 CI 매트릭스 (5단계 피라미드) 가 servlet5/6/61 셀로 구성되어 있다고 가정 (본문 미독). 본 결정으로 servlet61 셀이 살아 있어야 함을 확인.

## 11. 부록 — 통합 옵션이 권장되는 *가상의* 조건

만약 다음 조건이 **모두** 성립한다면 통합(옵션 B)이 재평가될 만하다:

| 조건 | 현황 |
|---|---|
| (a) 사용자 베이스가 6.0 또는 6.1 한쪽으로 극단 쏠림 (한쪽이 <10%) | 미충족. 2026-05 현재 양쪽 공존 |
| (b) 어댑터가 `sendRedirect(loc, sc, clearBuffer)` 등 6.1 신규 추상 메서드를 노출할 의무가 없음 | 미충족. Spring MVC 4.x 등이 호출할 가능성 |
| (c) 모듈 빌드/게시 자동화 비용이 본 어댑터 가치 대비 크게 큼 | 미충족. Toolchain 자동화로 비용 미미 |
| (d) 미래 6.2/7 등 추가 메이저가 곧 없을 것이라는 신호 | 미충족. EE 12 / Servlet 6.2 가 EE 로드맵에 등재 |

→ **현 시점에 통합을 권장할 조건이 하나도 충족되지 않음**. 분리 권장은 강고하다.
