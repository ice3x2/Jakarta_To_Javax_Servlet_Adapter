# 6. 양방향 변환 의미론 및 폴백 전략

본 장은 `javax.servlet 4.0` ↔ `jakarta.servlet 5.0 / 6.0 / 6.1` 어댑터가 **"상호 변환이 잘 되어야 한다"** 는 요구사항을 만족하기 위해 따라야 할 의미론(semantics) 명세를 도출한다. 코드 변경은 일절 다루지 않고, 명세·정책·trade-off 만 다룬다.

---

## 6.0. 요구사항 해석 검증

사용자 요구 **"상호 변환이 잘 되어야 한다"** 를 다음 4개의 명시 조건으로 해석한다.

| 조건 | 해석 | 검증 |
|---|---|---|
| C1 | 어떤 버전 페어든 변환 객체가 **인터페이스의 모든 추상 메서드를 구현**해야 한다 (abstract class 가 되지 않아야 한다). | 컴파일·`AbstractMethodError` 검증 |
| C2 | 변환 후 정보 손실이 **최소화**되어야 한다. | §6.10 정보 손실 인벤토리로 정량화 |
| C3 | 변환된 객체에 대한 호출이 **원본 객체로 충실히 위임**되어야 한다 (즉 어댑터는 본질적으로 Decorator 다). | §6.11 의 §SPEC-2~SPEC-4 |
| C4 | **시그니처 비대칭**이 발생해도 호출 시 합리적인 폴백 동작이 정의되어야 한다 (silent crash 금지). | §6.2 정책 매트릭스 |

**해석 적정성:** C1 은 자명하다 (안 그러면 클래스 로딩 자체가 깨진다). C3 은 어댑터의 본질이므로 비논쟁적. C2/C4 가 본 보고서의 핵심 결정 사항이다. C2 와 C4 는 trade-off 관계 (정보를 보존하려고 자체 상태를 두면 위임의 충실성 C3 이 약해진다). 따라서 **C3 을 1순위, C4 를 2순위, C2 를 3순위**로 두는 우선순위가 합리적이다. 본 보고서 전반은 이 우선순위를 따른다.

추가로, 사용자가 언급하지 않았지만 본 어댑터가 만족해야 할 묵시적 요구를 명시화한다:

| 조건 | 내용 |
|---|---|
| C5 (스레드 안전성) | 어댑터 인스턴스는 원본의 스레드 안전성 계약을 그대로 승계한다 (어댑터 자체가 새 mutable state 를 도입하지 않는 한). |
| C6 (성능 부담 최소화) | 호출당 메모리 할당은 원본 호출 비용의 동일 차수 이내. |
| C7 (개발자 진단 용이성) | 폴백·정보손실이 발생했음을 사용자가 인지·진단할 수 있어야 한다 (적어도 로그·옵션으로). |

## 6.1. 비대칭 시그니처 전수 매트릭스 (Q1)

### 6.1.1 표기 약속

- **존재(O)** : 인터페이스에 메서드가 존재하고 정상 사용 가능.
- **(D)** : 존재하나 `@Deprecated`. 호출 가능.
- **(DR)** : `@Deprecated(forRemoval=true)`. 다음 메이저에서 제거 예고.
- **부재(X)** : 인터페이스에서 제거됨 (또는 애초에 없음).
- **신규(N)** : 해당 버전에서 새로 추가.
- **default(DF)** : 인터페이스 default 메서드. implements 측에서 override 안 해도 됨.

기준점: javax 4.0.1, jakarta 5.0, 6.0, 6.1. ⚠ 표시 = 비대칭으로 인해 어댑터의 폴백 결정이 필요한 메서드.

## 6.2. 폴백 정책 결정 매트릭스 (Q2)

### 6.2.1 정책 알파벳

| 코드 | 정책 | 적합 조건 | 부적합 조건 |
|---|---|---|---|
| **A** | `UnsupportedOperationException` (or specific subclass) | 의미를 가짜로 재구성하면 더 위험. 명시적 실패가 사용자에게 더 유익. | 사용자가 try/catch 를 강제로 둘러야 하는 부담. 라이브러리 호환성 깨짐. |
| **B** | attribute API 자동 폴백 | getValue↔getAttribute 처럼 의미가 동일하거나 유사. | 의미가 미묘하게 다를 때 (예: 가시성 범위가 다름). |
| **C** | no-op (void) | 부수효과가 비대칭 영향이 없을 때 (setter 무시). | 사용자가 영구 무시를 인지 못하면 silent bug. |
| **D** | 기본값 반환 (null/false/0/"") | 사용자 코드가 null check 등 정상 처리 패턴을 따른다는 전제. | 0/false 가 의미 있는 값일 때 (예: id=0 이 잘못된 id 와 구분 안 됨). |
| **E** | 다른 메서드 우회 (encodeUrl→encodeURL) | 단순 deprecation alias. | alias 가 미묘한 동작 차이를 가질 때. |
| **F** | 자체 상태 보존 + 응답 합성 | 어댑터가 정보를 보관해 두고 응답 시 직접 직렬화. | 응답 단계와 결합이 필요해 어댑터 책임 범위가 늘어남. |
| **G** | 시스템 프로퍼티/init-param 으로 토글 | 사용자 환경마다 적절한 답이 다름 (strict vs. lenient). | 옵션 폭발, 디폴트 결정 부담. |

### 6.2.2 권장 정책 (방향별)

표기: **javax→jakarta** = `adapter.jakarta.servlet.*` (원본은 javax, 인터페이스는 jakarta). **jakarta→javax** = `adapter.javax.servlet.*`.

### 6.2.3 `HttpSession.getValue/putValue/removeValue/getValueNames` 자세히

**시나리오:** 사용자가 javax 4 코드를 작성. jakarta 6 컨테이너 위에서 실행. 원본은 jakarta 6 `HttpSession`. 어댑터 `adapter.javax.servlet.http.HttpSession` 가 javax 4 `HttpSession` 인터페이스를 구현해 사용자에게 반환됨. 사용자가 `session.getValue("foo")` 호출.

**상태:** 어댑터는 jakarta 6 원본의 `getValue` 를 호출할 수 없다 (인터페이스에 부재). 두 폴백 정책 후보:

| 후보 | 동작 | 장점 | 단점 |
|---|---|---|---|
| B. `getAttribute("foo")` 로 자동 폴백 | spec 자체가 두 메서드의 의미를 동일하게 정의했었음 (`getValue` 는 `getAttribute` 의 단순 alias 였음). | 사용자 코드 무변경. silent 호환. | "silent migration" 이 일어났음을 사용자가 인지 못함. attribute namespace 가 동일하므로 의미 일치는 확실 |
| A. `UnsupportedOperationException` | 명시적 실패. 사용자가 코드를 `getAttribute` 로 변경하도록 유도 | 안전. 새 정보 누락 없음 | javax 4 잔존 라이브러리(예: Struts 1, 일부 레거시 JSP) 가 호환되지 않음 |

**판정:** **B 가 권장 default**. Servlet spec 의 javadoc 자체가 이 두 메서드의 의미를 동일하게 정의했고(`getValue` 는 단순 deprecated alias 였음), B 폴백은 의미상 손실이 없다. **로그 WARN once-per-method** 로 사용자에게 알린다. strict 모드에서만 A.

`getValueNames()` 는 `getAttributeNames()` 의 `Enumeration<String>` 을 `String[]` 으로 한 번 더 박싱한 동등물이다. 동일 근거로 B 권장.

`getSessionContext()` 는 의미가 다르다. javax 측의 javadoc 도 `HttpSessionContext` 가 모든 메서드를 더 이상 의미 있는 값을 반환하지 않아도 된다고 명시한다(보안상 sessionId 목록 노출 위험). 따라서 **D (더미 반환)** 가 spec 권장 동작. 어댑터의 더미는:
- `getSession(String id)` → `null`
- `getIds()` → empty `Enumeration`

이 더미는 어댑터 패키지 내 자체 클래스 `EmptyHttpSessionContext` 등으로 두면 된다. (이미 `adapter.javax.servlet.http.HttpSessionContext` 가 jakarta 의 `HttpSessionContext` 를 wrap 하지만, jakarta 6 부터는 wrap 대상이 없어진다. 6.x source-set 에서는 더미로 대체.)

### 6.2.4 `Cookie.setAttribute("SameSite", "Lax")` 자세히

**시나리오:** 사용자가 jakarta 6 코드 작성. javax 4 컨테이너 위에서 실행. (또는 반대 — 어쨌든 jakarta 6 측에 attribute API 가 존재하고 javax 측에 없음.)

방향별로 분석:

**방향 (a): jakarta→javax (사용자가 jakarta 6 Cookie 호출, 원본은 javax 4 Cookie)**

이 시나리오는 흔치 않다. (보통은 javax 4 코드를 jakarta 6 컨테이너 위에서 돌리는 게 정방향.) 그래도 가능:
- 사용자가 `cookie.setAttribute("SameSite", "Lax")` 호출.
- 어댑터는 javax 4 `Cookie` 의 적절한 메서드를 모름.
- **유일한 해결:** 어댑터에 자체 Map 보관 + 어댑터를 wrap 한 응답이 `addCookie(cookie)` 호출될 때 Set-Cookie 헤더에 직접 직렬화 추가.

**방향 (b): javax→jakarta (사용자가 jakarta 6 코드, 원본은 javax 4)**

더 흔하다 (정방향). javax 4 사용자가 `cookie.setAttribute("SameSite", "Lax")` 같은 호출을 javax 인터페이스를 통해 시도할 수 없다 (javax 4 인터페이스에 메서드가 없음). 즉 javax 4 사용자 코드는 처음부터 attribute 를 사용하지 않는다. jakarta 6 컨테이너가 javax 4 어댑터로 wrap 된 Cookie 를 받아 처리할 때, 사용자가 jakarta 6 API 로 attribute 를 추가하지는 않으므로 손실이 발생할 경로가 없다.

**판정 (방향 a, jakarta→javax):**

| 후보 | 동작 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| F1 | 어댑터 Cookie 자체에 attribute Map 보유 + addCookie 시 응답 헤더 합성 | 의미 완전 보존 | 어댑터 Cookie 가 더 이상 단순 Decorator 가 아님. 응답 객체와 결합. 모든 addCookie 경로(직접/Filter/AsyncContext 등)에서 합성 로직이 실행되도록 보장 어려움 | △ 복잡 |
| F2 | 어댑터 Cookie 의 attribute Map 만 보유 + 사용자가 Set-Cookie 를 직접 직렬화하는 라이브러리에 의존 | 어댑터 단순 | 사용자 코드 변경 필요 | × |
| D | no-op + WARN (set), null/empty (get) | 단순 | 정보 손실 | 권장 default |
| A | UnsupportedOperationException | 안전 | jakarta 6 신규 코드가 javax 4 컨테이너에서 깨짐 | strict 모드 |

**default 권장: D + WARN.** 이유:
1. javax 4 컨테이너에서 jakarta 6 Cookie attribute 가 실제로 응답 헤더에 반영되어야 하는 시나리오는 매우 좁다 (Cookie attribute API 가 7.x 라이브러리 표준이 되기 전까지는).
2. F1 의 복잡도는 어댑터의 책임 경계를 크게 흐트러뜨린다. 어댑터 Cookie 가 자체 상태를 갖게 되면 cloning, equality, thread-safety 모두 복잡해진다.
3. 어쨌든 jakarta 6 native Cookie attribute 를 100% 활용하려면 jakarta 6 컨테이너 위에서 jakarta 6 코드를 직접 실행해야 한다. 어댑터를 우회하라는 안내가 맞다.

**문서로 손실을 명시화**하면 D 가 충분히 합리적이다.

### 6.2.5 `ServletRequest.getRequestId()` 자세히 (방향: javax→jakarta 6+)

**상태:** javax 4 측 `ServletRequest` 에 대응 메서드 부재. 어댑터가 jakarta 6 `ServletRequest` 추상 메서드를 구현해야 함 (안 그러면 추상 클래스).

**spec 요구사항 (jakarta 6 javadoc):**
- `getRequestId()` 는 컨테이너 내에서 unique 한 id 반환. 같은 요청에 대한 반복 호출은 같은 값 반환.
- `getProtocolRequestId()` 는 protocol-specific id (HTTP/2 stream id 등). 없으면 `""`.

**구현 후보:**

| 후보 | 구현 | 장점 | 단점 |
|---|---|---|---|
| F1 | 어댑터에 final UUID 필드 + 생성자에서 1회 생성 | spec 만족 (같은 요청에 같은 값) | 같은 javax request 를 두 번 wrap 하면 두 어댑터가 서로 다른 UUID 를 가지게 됨 (참조 동일성 결여) |
| F2 | javax request 의 `getAttribute("com.snoworca.adapter.requestId")` 에 lazy 저장 | 같은 javax request 에 대해 같은 id | request 가 새로 시작될 때 attribute 가 비어 있다는 가정 의존. 컨테이너가 attribute 를 직렬화할 수 있는 환경에서는 부작용 가능 |
| D | UUID 매번 새로 생성 | 단순 | spec 위반 (반복 호출이 다른 값) |

**권장: F2.** request attribute 가 request 라이프사이클과 동일하므로 가장 정확한 매핑. 같은 원본을 여러 번 wrap 해도 모두 같은 id 를 본다.

```
RequestId resolution rule:
  if request.getAttribute(KEY) == null:
    request.setAttribute(KEY, UUID.randomUUID().toString())
  return (String) request.getAttribute(KEY)
```

`getProtocolRequestId()` 는 javax 4 에서 얻을 수 없는 정보 → **D (`""` 반환)**. spec 도 이 값을 디폴트로 허용.

`getServletConnection()` 은 새 객체. 어댑터가 javax `request` 의 정보로 구성한 dummy 반환:
- `getConnectionId()`: request 의 attribute 에 lazy 저장된 UUID
- `getProtocol()`: `request.getProtocol()`
- `getProtocolConnectionId()`: `""`
- `isSecure()`: `request.isSecure()`

→ **F**.

## 6.3. 변환의 항등성과 단방향성 (Q3)

### 6.3.1 현재 상태 (`ServletAdapter` L18-20, L26-28 등)

```java
public static javax.servlet.http.HttpServletResponse adaptToJavax(javax.servlet.http.HttpServletResponse response) {
   return response;     // 그대로 반환 (이미 javax 면 wrap 안 함)
}
```

→ **homogeneous wrap (같은 namespace) 은 회피**. 이는 좋은 설계. 하지만:

### 6.3.2 다중 wrapping 시나리오

```
jakartaReq1                   -> adaptToJavax(jakartaReq1) -> javaxAdapter1
javaxAdapter1                 -> adaptToJavax(javaxAdapter1) -> javaxAdapter1   (위 패턴으로 OK)
javaxAdapter1                 -> adaptToJakarta(javaxAdapter1) -> jakartaAdapter2  ← 새로 wrap
jakartaAdapter2 (instanceof jakarta.servlet.http.HttpServletRequest)
                              -> adaptToJavax(jakartaAdapter2) -> javaxAdapter3  ← 또 wrap
```

**문제:**
1. `jakartaAdapter2` 는 jakarta 6 API 를 구현하지만 내부적으로는 javax 어댑터를 wrap 하고 있다. 호출이 두 번의 위임을 거친다 (jakarta→javax→jakarta 원본). 성능 손실.
2. `jakartaAdapter2 ≠ jakartaReq1` (identity). 두 wrapper 인스턴스가 같은 원본을 가리키지만 서로 다른 객체.
3. `equals/hashCode` 는 `Object.equals` (참조 동일성) → 두 wrapper 는 같지 않다.

### 6.3.3 unwrap 식별 인터페이스

어댑터에 unwrap 가능 marker interface 를 도입하면 다중 wrap 회피 가능:

```
interface AdapterUnwrap<T> {
    T unwrap();   // 원본 반환
}
```

`ServletAdapter.adaptToJavax(jakartaObj)` 의 사전 체크:
```
if (jakartaObj instanceof AdapterUnwrap):
    Object src = ((AdapterUnwrap<?>) jakartaObj).unwrap()
    if src instanceof javax.servlet.http.HttpServletRequest:
        return (javax.servlet.http.HttpServletRequest) src   // 원본 반환, wrap 안 함
```

→ **불필요한 wrap 회피**. 항등성 보장 (`adaptToJavax(adaptToJakarta(javaxObj)) == javaxObj`).

**판정:** §6.11 의 SPEC-5 로 명시화 권장.

### 6.3.4 기존 코드의 잠재 결함

현재 ServletAdapter 는 `adaptToJakarta(javax X)` 만 있고 `adaptToJakarta(jakarta X)` (homogeneous) 가 없다. 따라서 jakartaAdapter 를 다시 `adaptToJakarta` 에 넣으려면 사용자가 직접 `adaptToJavax(jakartaAdapter)` → `adaptToJakarta(...)` 의 2단계를 거쳐야 한다. 이는 사실상 *명시적인 unwrap 부재로 인한 다중 wrap 강제*.

호환성을 위해 `adaptToJakarta(jakarta X)` 같은 homogeneous 오버로드도 추가하는 게 자연스럽다 (현재의 `adaptToJavax(javax X)` 패턴과 대칭).

## 6.4. 객체 그래프 변환의 일관성 (Q4)

### 6.4.1 현재 상태

`adapter.jakarta.servlet.http.HttpServletRequest:111-117`:
```java
@Override public jakarta.servlet.http.HttpSession getSession() {
   return new HttpSession(this.httpRequest.getSession());   // 매 호출마다 new
}
```

`getSession()` 을 두 번 호출하면 두 개의 새 `adapter.jakarta.servlet.http.HttpSession` 인스턴스가 반환된다. 두 인스턴스는 같은 원본을 wrap 하지만 서로 다른 객체. 사용자 코드:
```java
HttpSession s1 = request.getSession();
HttpSession s2 = request.getSession();
assert s1 == s2;   // FAIL (servlet spec 은 보통 같은 인스턴스 보장하나, 어댑터는 깬다)
```

**현재 시점에서 깨지는 사용자 코드:**
- spec 은 `request.getSession()` 이 같은 세션을 반환한다고 정의함. `==` 비교를 하는 사용자는 별로 없지만, `s1.equals(s2)` 가 항상 `true` 이어야 한다는 묵시적 계약은 존재할 수 있다. 어댑터가 wrap 하면 equals 가 Object default (참조 동일성) 이므로 `s1.equals(s2) == false`.

### 6.4.2 캐싱 (wrapper pool) 옵션

| 옵션 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 옵션 1 | 매 호출마다 new (현재) | 메모리 단순. GC 자연스러움 | 동일 원본에 대해 wrap 비대칭 |
| 옵션 2 | `WeakHashMap<원본, WeakReference<래퍼>>` 캐시 | 같은 원본에 대해 같은 wrapper 반환 | 동시성 제어 필요. WeakReference 만료 시 race condition |
| 옵션 3 | 원본의 attribute 에 wrapper 저장 (`originalReq.setAttribute("adapter.wrapper", this)`) | spec 친화 | attribute namespace 오염 |
| 옵션 4 | `equals/hashCode` override (원본 동일성으로 위임) | 캐시 없이도 동등성 보장 | `==` 는 여전히 다름. equals 만 보장 |

**권장: 옵션 4 (default) + 옵션 2 (opt-in).** equals/hashCode 만으로도 대부분의 사용자 코드는 호환된다. `==` 비교가 필요한 (드문) 사용자만 opt-in 으로 캐싱을 켤 수 있게.

```
@Override
public boolean equals(Object o) {
    if (o instanceof AdapterUnwrap) {
        return this.unwrap().equals(((AdapterUnwrap<?>) o).unwrap());
    }
    return false;
}
@Override public int hashCode() { return this.unwrap().hashCode(); }
```

캐싱(옵션 2) 의 메모리/일관성 분석:
- 메모리: request 라이프사이클(요청 단위) 내에서 wrapper 인스턴스 수는 N (그래프 노드 수). request 종료 시 GC.
- 일관성: 컨테이너가 request 객체를 재사용하면 (드물지만 가능) 캐시도 reset 되어야 함. WeakHashMap 만으로는 충분치 않을 수 있음.

**판정:** §6.11 SPEC-6 으로 옵션 4 default, 옵션 2 future work 으로 둠.

## 6.5. 예외 변환 (Q5)

### 6.5.1 현재 상태

`adapter.jakarta.servlet.http.HttpServletRequest:23-25`:
```java
try { ... }
catch (javax.servlet.ServletException var4) {
   throw new ServletException(var4);  // cause chain 으로 javax 예외 보존
}
```

→ `jakarta.servlet.ServletException` 의 cause 에 원본 `javax.servlet.ServletException` 이 들어감. Stack trace 도 보존.

### 6.5.2 ServletException 시그니처 변화 (5→6)

| 생성자 | 5.0 | 6.0 | 6.1 |
|---|---|---|---|
| `ServletException()` | O | O | O |
| `ServletException(String)` | O | O | O |
| `ServletException(String, Throwable)` | O | O | O |
| `ServletException(Throwable)` | O | O | O |
| `getRootCause()` | O | **O (D)** | O (D) |

**변화:** 6.0 에서 `getRootCause()` 가 deprecated (`Throwable.getCause()` 로 대체). 어댑터의 위임 코드(`throw new ServletException(var4)`) 는 영향 없음. `getRootCause()` 를 직접 호출하는 코드만 deprecation 경고.

`getRootCause()` 가 deprecated 이지만 인터페이스에서 제거되지는 않았으므로 어댑터는 그대로 호출 가능.

### 6.5.3 다른 예외 (`IllegalStateException` 류)

`IllegalStateException` 은 `java.lang` 의 RuntimeException 이므로 네임스페이스 분기 없음. 양방향 그대로 throw 가능. 어댑터가 별도 변환 불필요.

`UnsupportedOperationException` 도 동일.

`IOException` 도 `java.io` 의 표준 예외이므로 동일.

### 6.5.4 변환된 예외의 stack trace 보존

`new ServletException(var4)` 는 새 stack trace 를 가지지만 `var4` 가 cause 로 chain. 사용자가 `getCause()` 호출 시 원본 예외와 그 stack trace 를 그대로 받음.

**잠재적 손실:** `ServletException` 의 추가 정보(예: spec 의 `rootCause` 필드)가 cause chain 의 깊이에 따라 일부 분실될 가능성. 하지만 spec 상 `rootCause = getCause()` 이므로 실질 손실 없음.

**판정:** 예외 변환은 현재 코드가 적절함. 별도 변경 불필요.

## 6.6. 컬렉션·배열 변환의 lazy vs eager (Q6)

### 6.6.1 현재 상태

`adapter.jakarta.servlet.http.HttpServletRequest:166-175` (getCookies):
```java
javax.servlet.http.Cookie[] cookies = this.httpRequest.getCookies();
ArrayList<jakarta.servlet.http.Cookie> newArrayList = new ArrayList<>();
for (javax.servlet.http.Cookie cookie : cookies) {
   newArrayList.add(new Cookie(cookie));
}
return newArrayList.toArray(new jakarta.servlet.http.Cookie[0]);
```

→ **eager**. 호출 즉시 모든 Cookie 를 새 인스턴스로 wrap, 새 배열 할당.

`getParts()`, `getServletRegistrations()`, `getFilterRegistrations()` 도 모두 eager 새 컬렉션 생성 + 항목 wrap.

### 6.6.2 lazy 변환의 trade-off

| 측면 | eager (현재) | lazy (Iterator/Stream 기반) |
|---|---|---|
| 메모리 | N개 wrapper 즉시 할당 | 호출당 1개 wrapper |
| 호출 latency | 첫 호출에 대량 작업 | 각 호출에 작은 작업 분산 |
| 원본 mutation 가시성 | 호출 시점 snapshot | 호출 시점에 실시간 |
| 코드 복잡도 | 단순 | Iterator/Iterable wrap 필요 |
| sub-collection wrap 일관성 | wrap 된 collection 의 mutation 이 원본에 반영 안 됨 (snapshot) | 반영됨 (lazy view) |

`Cookie[]` 같은 배열은 lazy 변환이 어렵다 (배열은 인덱스로 임의 접근). lazy 화하려면 `Iterable<Cookie>` 같은 별도 인터페이스가 필요한데, spec 이 배열을 강제하므로 어댑터는 eager 외 선택지 없음.

`Collection<Part>` 는 lazy view 가능. 단 spec 은 immutable 한 snapshot 을 권장하므로 eager 가 spec 친화.

`Map<String, ServletRegistration>` 도 보통 등록 시점 snapshot. lazy 화 가치 낮음.

### 6.6.3 부작용 — 원본 컬렉션 mutation

eager 컬렉션의 mutation 은 원본에 반영 안 됨. spec 상 `getCookies()` 등은 immutable snapshot 을 반환하는 게 자연스러우므로 이 동작이 맞다.

단 `getServletRegistrations()` 같은 dynamic 한 컬렉션은 모순:
- 어댑터가 eager copy 후 사용자가 새 Servlet 을 등록 → 새 등록은 어댑터가 반환한 Map 에 보이지 않음 (사용자가 다시 호출해야 함). spec 자체도 보통 immutable view 를 권장.

**판정:** 현재 eager 가 합리적. 단 **새 Map 객체를 매번 반환**하는 코드는 호출 횟수에 비례해 메모리 압박. lazy view (LinkedHashMap 등 한 번 만들고 캐싱 또는 view wrapper) 가 가치 있을 수 있으나, 우선순위 낮음.

## 6.7. 스트림·Listener 변환 (Q7)

### 6.7.1 현재 코드 검토

`StreamConverter` (Q7 핵심):

**버그 식별:**
1. **`read(byte[] b, int off, int len)` 의 `readLine` 호출 (L41, L93):** `ServletInputStream.readLine` 은 line termination 까지 읽는 다른 의미의 메서드. `read(b, off, len)` 의 의미와 다름. **버그.**
   ```java
   public int read(byte[] b, int off, int len) throws IOException {
      return inputstream.readLine(b, off, len);   // ← 오류. inputstream.read(b, off, len) 가 맞음
   }
   ```
   → §6.12 결함 인벤토리에 기록.

2. `read(byte[] b)` 가 `read(b, 0, b.length)` 로 redirect 되는데, `readLine` 호출 버그 때문에 결과적으로 `readLine(b, 0, b.length)` 가 호출됨. **광범위한 잘못된 의미.**

3. `isFinished/isReady` 의 fallback 시도 (L121-135) 는 `inputstream.isFinished/isReady` 가 throw 할 경우를 가정. 정상적인 ServletInputStream 은 이들을 throw 하지 않으므로 fallback 은 작동 안 함. 불필요한 방어 코드.

4. `setReadListener` 위임은 `ReadListenerConverter.convert(arg0)` 로 정확. 단 `ReadListenerConverter.convert(javax.servlet.ReadListener)` 가 jakarta 측 `ReadListener` 를 반환해 jakarta 의 `inputstream.setReadListener` 에 넘기는 흐름은 jakarta 5/6 모두 동일. 시그니처 변화 없음.

### 6.7.2 ReadListener / WriteListener 변경

| 메서드 | javax 4 | jakarta 5 | jakarta 6 | jakarta 6.1 |
|---|---|---|---|---|
| `ReadListener.onDataAvailable/onAllDataRead/onError` | O | O | O | O |
| `WriteListener.onWritePossible/onError` | O | O | O | O |

→ **변화 없음.** 어댑터의 `ReadListenerConverter`, `WriteListenerConverter` 는 어느 버전에서도 그대로 사용 가능.

### 6.7.3 thread-safety

ReadListener / WriteListener 콜백은 컨테이너가 임의의 스레드에서 호출. 어댑터는 단순 위임이므로 추가 동기화 불필요. 사용자가 작성한 listener 가 thread-safe 인지에 모든 책임이 위임됨.

단 `StreamConverter.convert(ServletInputStream).isFinished` 가 `try/catch` 후 멤버 변수 (`this.isFinished`) 에 의존. 이는 anonymous inner class 인스턴스 한 개 안에서만 보이므로 thread 사이에서 stale read 가능. `volatile` 부여 필요. (현재 코드의 결함)

### 6.7.4 판정

스트림 변환의 핵심 버그 (`readLine` 오용)는 어댑터의 정확성을 심각하게 깬다. **§6.12 의 결함 우선순위 1번** 으로 기록. 6.x source-set 분기 작업 시 함께 수정 권장.

## 6.8. AsyncContext 변환 (Q8)

### 6.8.1 시그니처 보존

`AsyncContextConverter` 는 anonymous class 로 양방향 위임. `dispatch / complete / setTimeout / start / addListener / createListener / hasOriginalRequestAndResponse / getRequest / getResponse / getTimeout` 모두 단순 위임. 의미 보존 OK.

### 6.8.2 AsyncListener 등록·해제

`addListener` 는 변환된 listener 를 원본 컨테이너에 등록. 등록 해제는 spec 상 `complete` 시점에 자동. 어댑터가 별도 unregister 호출 안 함. spec 동작 동일.

`AsyncEvent.getAsyncContext` / `getSuppliedRequest/Response/Throwable` 모두 변환. `Throwable` 은 java.lang.* 이므로 동일 인스턴스. 의미 일치.

### 6.8.3 잠재 문제

**잠재 결함:** `AsyncContextConverter.convert(javax.servlet.AsyncListener)` 가 anonymous class 를 매 호출마다 새로 생성. 같은 listener 를 두 번 등록 후 한 번만 해제하려는 경우 어댑터가 만든 두 anonymous 인스턴스가 서로 다르므로 unregister 가 동작 안 함. 단 servlet spec 의 AsyncListener 는 일반적으로 자동 해제이므로 실용적 문제 없음.

**판정:** 현재 코드 OK.

## 6.9. 변환 정책의 사용자 노출 (Q9)

### 6.9.1 사용자가 폴백을 인지·제어해야 하는가

C7 (개발자 진단 용이성, §6.0) 에 따라 **YES**. 다음 두 가지가 필요:

1. **로깅** — 폴백이 발생할 때 WARN once-per-method emit. java.util.logging 또는 SLF4J 의 어느 것이든 무관 (logger 의존성 없는 어댑터는 java.util.logging 이 무난).
2. **시스템 프로퍼티 / init-param 토글** — `com.snoworca.adapter.strict=true` 면 모든 폴백 대신 `UnsupportedOperationException` throw.

### 6.9.2 로깅 정책

| 레벨 | 사용처 |
|---|---|
| WARN | 폴백이 silent migration 으로 동작하는 경우 (예: getValue→getAttribute) |
| INFO | 동일 의미 alias 가 호출됨 (예: encodeUrl→encodeURL) |
| FINE | 디버그 용. 모든 변환 호출 추적 |

once-per-method: WeakHashMap<String, Boolean> 또는 ConcurrentHashMap.putIfAbsent 로 메서드명 키 기반 dedup.

### 6.9.3 diagnostics API

```
ServletAdapter.diagnostics() -> Map<String, Long>
  // key: 메서드 이름 (예: "HttpSession.getValue"), value: 호출 횟수
```

→ 운영 환경에서 폴백 호출량을 측정 가능. opt-in 으로 활성화 (성능 오버헤드 회피).

**판정:** §6.11 SPEC-7, SPEC-8 로 명시화.

## 6.10. 정보 손실 인벤토리 (Q10)

| # | 정보 | 손실 방향 | 등급 | 비고 |

| L15 | `ServletInputStream.read(byte[], int, int)` 의 데이터 정확성 | 양방향, `readLine` 오용 (StreamConverter L41, L93) | **C** | 데이터가 line terminator 까지만 읽힘. 바이너리 데이터 손상. 현재 코드의 가장 심각한 결함 중 하나 |
| L16 | `ServletResponse.setContentLengthLong(long)` 의 long 정밀도 | jakarta→javax (`adapter.jakarta.servlet.ServletResponse:81`), `(int)arg0` 으로 narrow | **C** | 2GB 이상 응답에서 길이 잘림 |
| L17 | `ServletContext.setResponseCharacterEncoding` (jakarta `ServletContext.java:338`) → `this.setRequestCharacterEncoding(arg0)` 호출 | request/response 가 바뀜 | **C** | response encoding 을 설정하려는 호출이 request encoding 에 적용됨. 현재 코드의 결함 |
| L18 | `ServletContext.setRequestCharacterEncoding` (javax `ServletContext.java:363`) → `this.setResponseCharacterEncoding(encoding)` 호출 | 반대 방향. request/response 가 바뀜 | **C** | 동일 종류의 결함 |

→ **C 등급 6건은 모두 6.x 지원 전에 우선 해결 권장**. §6.12 참조.

## 6.11. 권장 변환 의미론 명세 (Q11)

다음은 어댑터가 모든 버전 페어에서 따라야 할 명세다. 각 항목은 SPEC 식별자로 후속 plan/test 에서 참조 가능하도록 한다.

### SPEC-1. 인터페이스 완전 구현
어댑터 클래스는 대상 인터페이스의 모든 추상 메서드를 구현한다. 폴백이 정의되지 않은 추상 메서드가 존재하면 컴파일 실패로 즉시 알린다.

### SPEC-2. 위임 우선 원칙
어댑터는 위임 가능한 모든 호출을 원본에 즉시 위임한다. 새 인스턴스 합성, 자체 상태 보관, 정보 합성은 위임 불가능한 경우에만 수행한다.

### SPEC-3. 변환 합성 일관성
원본 메서드 반환값이 다른 namespace 의 타입이면 즉시 적절한 어댑터로 wrap 한다. wrap 정책은 다음을 따른다:
- (a) wrap 대상이 이미 어댑터(`AdapterUnwrap`) 이면 unwrap 후 원본 또는 그 직속 wrap 을 반환 (이중 wrap 회피).
- (b) wrap 대상이 일반 원본이면 새 어댑터 인스턴스를 반환.

### SPEC-4. 예외 변환
원본에서 throw 된 namespace-specific 예외 (`ServletException`) 는 동일 의미의 대응 namespace 예외로 변환하며, 원본 예외를 `cause` 로 chain 한다. `java.lang/java.io` 의 표준 예외는 그대로 propagate 한다.

### SPEC-5. 항등성 보장
`adaptToX(adaptToY(obj)) == obj` 가 `obj` 가 X namespace 의 객체이고 어댑터가 unwrap 가능한 경우 성립한다. `AdapterUnwrap<T>` marker 인터페이스를 도입해 어댑터가 자체 원본을 노출한다.

### SPEC-6. equals/hashCode 위임
모든 어댑터는 `equals` 와 `hashCode` 를 원본 객체로 위임한다. 같은 원본을 wrap 한 두 어댑터는 `equals` 가 `true` 를 반환한다. `==` 동일성은 보장하지 않는다 (캐싱 미도입 default).

### SPEC-7. 폴백 정책 정의
모든 비대칭 메서드(§6.1 의 ⚠) 는 §6.2.2 의 폴백 정책 매트릭스에 정의된 default 동작을 가진다. 정의되지 않은 비대칭 메서드는 SPEC-1 위반으로 간주한다.

### SPEC-8. 폴백 가시성
폴백이 발생할 때 어댑터는 다음을 보장한다:
- (a) 처음 발생 시 WARN 레벨 로그 (`com.snoworca.servletadapter` logger).
- (b) `ServletAdapter.diagnostics()` API 로 호출 통계 조회 가능 (opt-in 활성화).

### SPEC-9. strict 모드
시스템 프로퍼티 `com.snoworca.adapter.strict=true` 또는 init-param 으로 strict 모드 활성화 시, default 폴백(E/B/D/F) 대신 `UnsupportedOperationException` throw. 의도된 lenient 동작이 silent 결함을 가리는 운영 환경을 위한 토글.

### SPEC-10. 스레드 안전성
어댑터 자체는 새 mutable state 를 도입하지 않는 한 thread-safe 하다. RequestId 캐싱 등 자체 상태가 필요한 경우 request attribute 등 컨테이너가 제공하는 스레드 안전 보관소에 위임한다.

### SPEC-11. 컬렉션 변환
배열·컬렉션은 eager snapshot 으로 변환한다. 변환 시점의 원본 상태를 캡처하며 이후 원본의 mutation 은 반영하지 않는다.

### SPEC-12. Stream 변환 정확성
`read(byte[], int, int)` 등 모든 InputStream 메서드는 원본의 동일 시그니처 메서드로 위임한다. `readLine` 등 의미가 다른 메서드로의 임의 redirect 는 금지한다. (현재 코드 §6.12-D1 결함 수정 요청)

### SPEC-13. `setContentLengthLong`
`long` 길이를 위임 받는 모든 어댑터는 원본이 long 을 지원하면 `setContentLengthLong` 으로, 지원하지 않으면 `setContentLength((int)len)` 으로 위임하되 `len > Integer.MAX_VALUE` 일 때 IllegalArgumentException 을 throw 한다. (단순 narrow conversion 금지.)

### SPEC-14. 버전별 source-set
3개 버전 페어 (5/6/6.1) 는 별도 source-set 에서 빌드한다. 공유 코드는 메서드 시그니처가 동일한 영역에 한정한다. 폴백 정책은 source-set 별로 다르게 적용될 수 있다 (예: 5.0 source-set 은 SPEC-7 의 모든 ⚠ 가 위임 가능, 6.x source-set 만 폴백 활성화).

### SPEC-15. Cookie attribute 손실 명시
`Cookie.setAttribute` 등 jakarta 6+ 의 Cookie attribute API 는 javax 4 측에 매핑되지 않는다. default 정책은 D (no-op + WARN). 손실 가능성은 README 및 javadoc 에 명시한다.

### SPEC-16. 부수효과 보존
`flushBuffer`, `reset`, `resetBuffer`, `complete` 등 부수효과 메서드는 원본에 1:1 위임한다. 어댑터가 부수효과를 막거나 지연시키지 않는다.

## 6.12. 기존 코드의 변환 의미론 위반 (Q12)

본 절은 5.0 기반 현재 코드에서 식별된 결함을 나열한다. 수정은 본 보고서의 범위가 아니며 식별만 한다.

### D1 (Critical) — `StreamConverter` 의 `read(byte[], int, int)` 가 `readLine` 호출
**위치:** `adapter/servletElementConverter/StreamConverter.java:41, 93`

**증상:** `InputStream.read(byte[], int, int)` 의 의미는 임의 바이트를 읽는 것이지만 `ServletInputStream.readLine` 은 line terminator 까지만 읽는다. 어댑터를 통한 모든 byte read 가 line terminator 에서 멈춤. 바이너리 데이터 손상.

**의미론 위반:** SPEC-2 (위임 우선), SPEC-12 (stream 정확성).

### D2 (Critical) — `Part.getSubmittedFileName` 무한 재귀
**위치:** `adapter/jakarta/servlet/http/Part.java:50-56`

```java
@Override public String getSubmittedFileName() {
   try {
      return this.getSubmittedFileName();   // ← 자기 자신을 호출
   } catch (Exception e) {
      return this.getName();
   }
}
```

**증상:** `StackOverflowError` 발생 → catch → `getName()` 반환. 파일명이 항상 part name (form field name) 으로 잘못 반환됨.

**의도된 코드:** `return this.part.getSubmittedFileName();`

**의미론 위반:** SPEC-2 (위임 우선).

### D3 (Critical) — `ServletResponse.setContentLengthLong` 의 narrow 변환
**위치:** `adapter/jakarta/servlet/ServletResponse.java:81-83`

```java
@Override public void setContentLengthLong(long arg0) {
   this.response.setContentLength((int)arg0);   // ← long → int narrow
}
```

**증상:** `arg0 > Integer.MAX_VALUE (~2.1GB)` 시 silent overflow.

**의미론 위반:** SPEC-13 (setContentLengthLong 정확성). javax 4 측 `ServletResponse.setContentLengthLong(long)` 이 4.0 부터 존재하므로 어댑터는 `response.setContentLengthLong(arg0)` 로 위임 가능해야 한다.

### D4 (Critical) — `ServletContext.setResponseCharacterEncoding` 의 잘못된 redirect
**위치:** `adapter/jakarta/servlet/ServletContext.java:337-339`

```java
@Override public void setResponseCharacterEncoding(String arg0) {
   this.setRequestCharacterEncoding(arg0);   // ← request 에 설정
}
```

**증상:** response 인코딩 설정이 request 인코딩에 적용됨. response 인코딩이 default 로 잔존.

**의미론 위반:** SPEC-2 (위임 우선).

### D5 (Critical) — `adapter/javax/servlet/ServletContext.setRequestCharacterEncoding` 의 동일 종류 결함
**위치:** `adapter/javax/servlet/ServletContext.java:362-364`

```java
@Override public void setRequestCharacterEncoding(String encoding) {
   this.setResponseCharacterEncoding(encoding);   // ← response 에 설정
}
```

**증상:** D4 와 정반대 방향. request encoding 설정이 response encoding 에 적용됨.

**의미론 위반:** SPEC-2.

### D6 (Critical) — `HttpServletRequest.getContentLengthLong` 의 fallback 부정확
**위치:** `adapter/jakarta/servlet/ServletRequest.java:173-179`

```java
@Override public long getContentLengthLong() {
   try {
      return this.request.getContentLengthLong();
   } catch (Exception e) {
      return this.request.getContentLength();   // ← int → long widening, 그러나 long 형태로 손실
   }
}
```

**증상:** `getContentLengthLong` 이 정상 동작하지 않을 환경은 거의 없음. 또 fallback 이 int 길이를 반환하므로 2GB 이상 요청에서 잘못된 값.

**의미론 위반:** SPEC-2 (불필요한 방어 catch). 실용적 영향은 D3 보다 낮음 (보통 request 는 작음).

### D7 (Critical) — `adapter.jakarta.servlet.ServletRequest.getRealPath(String)` 호출
**위치:** `adapter/jakarta/servlet/ServletRequest.java:124-127`

```java
@Override public String getRealPath(String path) {
   return this.request.getRealPath(path);
}
```

**증상:** jakarta 5.0+ 의 `ServletRequest` 인터페이스에는 `getRealPath` 가 이미 없음. `@Override` 가 컴파일 통과되는 이유는 jakarta `ServletRequest` 가 아닌 부모(Object) 의 메서드를 override 한다는 잘못된 시도 (실제로는 컴파일 에러). 인덱스 문서가 §1.5 에서 이 부분의 정확성을 의심한 바 있음.

**확인 요청:** jakarta 5.0 `ServletRequest` interface 의 javadoc 을 재확인 후 어댑터 인터페이스 implements 여부 결정 필요.

### D8 (Acceptable) — `HttpServletResponse.encodeUrl` 의 `encodeURL` 위임
**위치:** `adapter/jakarta/servlet/http/HttpServletResponse.java:85-87`, `adapter/javax/servlet/http/HttpServletResponse.java:95-97`

```java
@Override public String encodeUrl(String url) {
   return this.httpResponse.encodeURL(url);   // ← 대문자 alias 로 위임
}
```

**평가:** spec 의 deprecated alias 동작과 일치. 그러나 사용자에게 silent migration 임을 알리지 않음 (no WARN). SPEC-8 (폴백 가시성) 보강 권장. **결함이라고 단정하긴 어려우나 정책 일관성 측면에서 로그 emit 권장.**

### D9 (Minor) — `adapter.javax.servlet.http.HttpServletRequest.getCookies` 의 null 케이스
**위치:** `adapter/javax/servlet/http/HttpServletRequest.java:182-191`

```java
public javax.servlet.http.Cookie[] getCookies() {
   jakarta.servlet.http.Cookie[] cookies = this.httpRequest.getCookies();
   // ← cookies 가 null 이면 다음 줄에서 NPE
   for (jakarta.servlet.http.Cookie cookie : cookies) { ... }
}
```

**증상:** spec 상 `getCookies()` 는 쿠키가 없으면 `null` 반환 가능. 어댑터가 null check 없이 즉시 enumerate → NPE.

(대칭으로 `adapter.jakarta.servlet.http.HttpServletRequest:167-175` 에도 동일 결함.)

**의미론 위반:** SPEC-2 의 정확한 위임 (null 결과를 그대로 통과시켜야 함).

### D10 (Minor) — `Cookie.<init>("ignored", "ignored")` 패턴
**위치:** `adapter/jakarta/servlet/http/Cookie.java:7`, `adapter/javax/servlet/http/Cookie.java:7`

**평가:** `Cookie` 가 클래스이므로 super() 호출이 필요. 부모의 `<init>(name, value)` 가 validation 을 수행하므로 ignored 값을 넘기는 게 일종의 trick. 실제 사용 시 getName/getValue 가 wrap 된 cookie 로 위임되므로 동작은 OK. 단 코드 가독성 측면에서 의도 표현이 부족.

**의미론 위반:** 없음. 단 `getName/getValue` 가 적절히 override 되었는지(현재 코드 확인됨, OK) 확인 필요.

### D11 (Minor) — `Cookie.clone()` 의 캐스트 안전성
**위치:** `adapter/jakarta/servlet/http/Cookie.java:71-73`

```java
return new Cookie((javax.servlet.http.Cookie)this.cookie.clone());
```

**평가:** `Object.clone()` 반환을 캐스트. `Cookie.clone()` 의 spec 은 항상 `Cookie` 인스턴스를 반환하므로 안전. 단 mismatch 시 ClassCastException 발생할 수 있음. 위임 코드로 충분하나 spec 명세에 더 엄밀히 대응하려면 cloneable 보장 명시 권장.

### D12 (Minor) — `HttpUpgradeHandler` 의 ThreadLocal 사용
**위치:** `adapter/jakarta/servlet/http/HttpUpgradeHandler.java:10-32`

**평가:** `ThreadLocal` 로 wrap 대상 클래스를 전달하는 hack. 동일 스레드 내에서 `request.upgrade(...)` 의 컨테이너 호출이 `HttpUpgradeHandler.<init>()` 를 동기 호출한다는 가정에 의존. 컨테이너가 비동기 또는 다른 스레드에서 `<init>` 호출 시 동작 안 함. **취약하지만 동작은 OK.** 더 안전한 대안 (factory 인터페이스 등) 이 가치 있으나 우선순위 낮음.

### D13 (Minor) — `HttpComponentConverter` 단방향
**위치:** `adapter/servletElementConverter/HttpComponentConverter.java`

**평가:** `convert(jakarta.servlet.DispatcherType) -> javax.servlet.DispatcherType` 만 정의. 반대 방향(`adapter.jakarta.servlet.ServletRequest:165-167`) 은 `DispatcherType.valueOf(this.request.getDispatcherType().name())` 로 직접 처리. 일관성 결여이나 의미는 동일.

## 6.13. 통합 권장 (요약)

본 보고서의 결정을 한 표로 응축한다.

| 영역 | 권장 |
|---|---|
| 비대칭 메서드 매트릭스 | §6.1 의 19개 표를 SPEC-7 의 입력으로 활용 |
| 폴백 default 정책 | §6.2.2 매트릭스. B (attribute alias), E (대문자 alias), D (no-op + WARN), F (UUID 합성) 위주 |
| strict 모드 | 시스템 프로퍼티 `com.snoworca.adapter.strict=true` 로 모든 default 폴백을 `UnsupportedOperationException` 으로 escalate |
| 항등성 | `AdapterUnwrap<T>` marker 도입 + `ServletAdapter` 의 모든 adaptTo* 에 unwrap 사전 체크 |
| equals/hashCode | 원본으로 위임 |
| 객체 그래프 캐싱 | default off. equals 위임으로 대체 |
| 예외 변환 | 현 코드 유지 (cause chain) |
| 컬렉션 | eager snapshot 유지. null 검사 추가 |
| stream | D1 결함 우선 수정 |
| AsyncContext | 현 코드 유지 |
| 가시성 | java.util.logging 의 WARN once + opt-in diagnostics() API |
| Cookie attribute | D (no-op + WARN) default. F (자체 Map + 응답 합성) 은 future work |
| Critical 결함 (D1~D7) | 6.x source-set 분기 작업 전·후로 모두 수정 권장 |

본 명세를 따르면 사용자 요구 **"상호 변환이 잘 되어야 한다"** 의 C1~C4 조건이 모두 만족 가능하며, 비대칭으로 인한 의미 손실은 §6.10 의 인벤토리에 제한되어 사용자에게 사전 공개 가능한 형태로 제어된다.
