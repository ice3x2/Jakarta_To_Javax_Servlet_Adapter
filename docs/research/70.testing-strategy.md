# 70. 테스트 전략 — 단위·계약·통합·크로스버전

## 0. 요약 (Executive Summary)

본 어댑터는 위임 위주(decorator) 모듈이라 표면적으로는 "테스트하기 쉬워 보이지만", 위임이 *조용히 잘못된 메서드를 호출*하거나 *시그니처 차이로 정밀도가 손실*되는 부류의 결함에 매우 취약하다. 현 코드 본만 정독해도 다음과 같은 **조용한 결함**이 즉시 발견된다.

| # | 위치 | 결함 |
|---|---|---|
| F1 | `adapter.servletElementConverter.StreamConverter#convert(jakarta.servlet.ServletInputStream)` L41 / L93 | `read(byte[], int, int)` 가 위임 대상의 `read` 가 아니라 `readLine` 을 호출 — 일반 바이트 읽기 시 라인 모드로 동작 |
| F2 | `adapter.jakarta.servlet.http.Part#getSubmittedFileName()` L52 | 자기 자신을 재귀 호출 — 첫 호출 시 즉시 `StackOverflowError` |
| F3 | `adapter.jakarta.servlet.ServletContext#setResponseCharacterEncoding(String)` L337-339 | `setRequestCharacterEncoding(arg)` 을 호출 — 응답 인코딩 설정 무효 + 요청 인코딩 오염 |
| F4 | `adapter.servletElementConverter.ServletReqResConverter#convert(jakarta.servlet.ServletResponse)` L22 | `instanceof javax.servlet.http.HttpServletResponse` 검사 — jakarta 객체가 javax 인터페이스를 구현할 리 없으므로 분기가 항상 `false` → HTTP 응답이 일반 `ServletResponse` 래퍼로 다운그레이드 (`HttpServletResponse` 메서드 호출 시 `ClassCastException`/누락) |
| F5 | `adapter.javax.servlet.http.HttpServletResponse` | `javax.servlet.http.HttpServletResponse#setContentLengthLong(long)` 위임 부재 — 인터페이스 기본 구현 없음, 컴파일은 통과하지만 호출 시 `AbstractMethodError` 또는 super 의 `setContentLength((int)long)` 정밀도 손실 |
| F6 | `adapter.jakarta.servlet.http.HttpServletResponse#setContentLengthLong` 등가, super (`ServletResponse`) 가 `(int)arg0` 캐스트로 정밀도 손실 |

`Part.getSubmittedFileName` 의 무한 재귀(F2)와 `StreamConverter.read` 가 `readLine` 을 호출하는 결함(F1) 은 **현 단위 테스트 2개로 결코 잡히지 않는다**. 회귀 테스트 슈트가 이 종류의 결함을 한 번에 잡지 못한다면 어떤 테스트 전략도 실패다.

본 문서는 이를 출발점으로 다음을 제시한다.

- **테스트 피라미드 5단계 (L1~L5)**, 각각의 비용/효과
- **source-set 별 테스트 분리** 토폴로지
- **Reflection 기반 contract 테스트** — 인터페이스 메서드 누락을 자동 검출
- **Tomcat embed** 통합 테스트 부트스트랩 코드
- **JUnit 5 Parameterized** 로 5/6/6.1 동등 동작 검증
- **GitHub Actions 매트릭스** yaml 예시
- **JaCoCo + PIT (mutation testing)** 적용 가이드
- **단계적 도입 로드맵 (Phase 1~5)**

## 1. Q1 — 현 테스트 상태 분석

### 1.1 파일·커버 범위

| 파일 | LOC | 무엇을 검증하나 |
|---|---|---|
| `src/test/java/com/snoworca/ServletContextAdapterTest.java` | 19 | mock jakarta `ServletContext.getContextPath()` 가 javax 어댑터를 통해 그대로 전달되는지 |
| `src/test/java/com/snoworca/ServletRequestResponseAdapterTest.java` | 31 | mock javax → adapt → mock jakarta → re-adapt 객체가 `null` 아님 |

→ **총 2개 파일, 정확히 3개 어설션 (`assertNotNull`/`assertEquals`).** 위임 메서드 1개(`getContextPath`)만 실질적으로 호출되며, 나머지 위임 메서드 약 250+개는 **단 한 줄도 호출되지 않음**.

### 1.2 Mock 패턴

`org.mockito:mockito-core:5.6.0` + `mockito-junit-jupiter:5.6.0`. 패턴은 단순 `mock(Class)` + `when().thenReturn()` 두 줄. `@ExtendWith(MockitoExtension.class)` 없음 → 명시적 stubbing 만으로 동작. `ArgumentCaptor`, `verify`, `RETURNS_DEEP_STUBS` 등 미사용.

### 1.3 커버리지 추정

JaCoCo 미적용. 위임 LOC 기준으로 추정:

| 영역 | 메서드 수 | 현재 호출되는 메서드 | 추정 라인 커버리지 |
|---|---|---|---|
| `adapter.jakarta.servlet.*` 위임 | ~80 | `getContextPath` (생성자 경로 포함 시 컨버터 진입) | < 5% |
| `adapter.javax.servlet.*` 위임 | ~80 | 0 (테스트가 mock 만 검증, 실제 메서드 호출 없음) | < 1% |
| `adapter.servletElementConverter.*` | ~50 | `ServletReqResConverter.convert(req)`/`convert(res)` 분기 1~2개 | ~5% |
| 예외 변환 try/catch | ~20 | 0 (예외 경로 미진입) | 0% |
| 컬렉션 복사·래핑 | ~10 | 0 | 0% |
| `ServletAdapter` 정적 팩토리 | 10개 오버로드 | 3개 (Request/Response/Context) | 30% |

→ **전체 라인 커버리지 추정 < 5%**, 분기 커버리지는 사실상 0%. F1~F4 결함은 이 커버리지에서 결코 드러나지 않는다.

### 1.4 통합 테스트 부재

실제 컨테이너에서 어댑터가 동작하는지 검증한 적이 0회. HTTP 요청·응답 사이클 전체에 어댑터를 끼워 본 적도 없음. 비동기, 멀티파트, WebSocket Upgrade, Cookie attribute 등 컨테이너 통합이 필수인 영역은 모두 검증 미달.

## 2. Q2 — 테스트 피라미드 5단계 (L1~L5)

```
        ┌──────────────────────────┐
   L5   │  호환성 회귀 (현 결함 박물관) │  ~10 케이스
        └──────────────────────────┘
       ┌────────────────────────────┐
  L4   │ Cross-version Matrix       │  Parameterized × 3 ver
       └────────────────────────────┘
      ┌────────────────────────────────┐
 L3   │ 통합 (Tomcat/Jetty embed)       │  ~30 시나리오
      └────────────────────────────────┘
     ┌──────────────────────────────────┐
L2   │ 의미론 (contract / property)      │  ~10 reflection driver
     └──────────────────────────────────┘
    ┌────────────────────────────────────┐
L1  │ 단위 (Mockito 위임 검증)              │  ~250 메서드
    └────────────────────────────────────┘
```

### 2.1 L1 — 단위 테스트 (Mock-based 위임 검증)

**무엇을 잡나**
- 위임 메서드가 원본의 **동명 메서드**를 호출하는지 (F1 같은 호출 대상 오타).
- 인자가 변형 없이(또는 약속된 변환만 거쳐) 전달되는지 (ArgumentCaptor).
- 반환값이 그대로(또는 약속된 래핑만 거쳐) 반환되는지.
- 정밀도 손실(`long → int`) 같은 명시적 변환 경계 (F5/F6).

**비용**
- JVM 단일 프로세스 내 실행. 약 250개 메서드 × 0.5ms ≈ 0.2초.
- mock 인스턴스 생성 + stubbing 비용은 무시 가능.
- 매트릭스 빌드에서도 부담 없음.

**ROI**
- **매우 높음.** F1/F2/F3 모두 L1 만으로 잡힌다. 단, **수기 작성 시 250개 테스트 보일러플레이트**가 문제. → L2 의 reflection contract 테스트로 자동 생성하라 (§5).

### 2.2 L2 — 의미론 테스트 (Contract / Property-based)

**무엇을 잡나**
- "어댑터는 인터페이스의 **모든** 추상 메서드를 위임해야 한다" 라는 메타 계약. 인터페이스에 새 메서드가 추가될 때 어댑터가 빠뜨리면 자동 검출.
- `f(g(x)) ≈ x` 같은 양방향 변환의 항등성 (`adaptToJavax(adaptToJakarta(req)) ≈ req`). 단 어댑터는 매번 새 래퍼를 만들므로 `==`가 아니라 *관찰 가능한 동작 동등성*만 검증.
- 변환 규약 위반 (예: `instanceof` 분기에서 잘못된 타입을 검사하는 F4).

**비용**
- reflection 호출 약간의 오버헤드. 인터페이스당 50~100 메서드 → 메서드당 mock + invoke + verify. 인터페이스 4~5개 검증 시 1~3초.

**ROI**
- **매우 높음.** 6.0/6.1 로 source-set 을 분리한 후 새 메서드 누락을 자동 검출하는 유일한 수단. 단발성 작성 비용으로 영구적 회귀 보호.

### 2.3 L3 — 통합 테스트 (실제 컨테이너 임베드)

**무엇을 잡나**
- 컨테이너가 어댑터를 통해 servlet 을 등록/호출/dispatch 할 때 실제로 동작하는지.
- HTTP 응답 헤더의 `Set-Cookie`, `SameSite`, charset, status code 등 *실제 와이어 포맷*.
- AsyncContext 의 thread/timing 동작.
- 멀티파트 업로드, ServletInputStream/OutputStream, Filter chain, ErrorPage dispatch.

**비용**
- Tomcat embed: 컨테이너 부팅 ~500ms~2s/테스트클래스, JVM fork 비용. 시나리오당 100~500ms.
- 시나리오 30개 × 평균 300ms ≈ 10초. 매트릭스 3개 버전 시 30초.
- 인프라 요구: `tomcat-embed-core`, `tomcat-embed-jasper`(필요 시), `httpclient5` 또는 JDK 11+ HttpClient.

**ROI**
- **높음.** F4(`instanceof` 잘못된 분기)는 통합 테스트만이 잡는다 — 단위 테스트는 분기 결과를 mock 으로 직접 입력하므로 못 잡는다.
- 단, 초기 도입 비용(부트스트랩 작성)이 가장 크다. 한 번 작성해 두면 재사용성 매우 높음.

### 2.4 L4 — 크로스 버전 호환성 매트릭스 테스트

**무엇을 잡나**
- 동일 시나리오를 5.0/6.0/6.1 어댑터 모듈에서 실행했을 때 **외부 관찰 가능한 결과(HTTP 응답)가 동등**한지.
- 5.0 에서는 동작하던 케이스가 6.0 에서 (예: `encodeUrl` 폴백) 깨지는지.
- 6.1 에서만 노출되는 신규 시그니처(`sendRedirect(loc,sc)`)가 5.0 호스트에서 무시되는지.

**비용**
- 매트릭스 = (Servlet 5×Java 8) ∪ (Servlet 6.0×Java 11) ∪ (Servlet 6.1×Java 17). CI 매트릭스로 빌드 분리. 로컬 빌드 시 3배 시간.

**ROI**
- **중간.** L1/L2/L3 가 source-set 별로 잘 짜여 있으면 L4 는 거의 자동으로 따라옴 (`@ParameterizedTest` 로 Tomcat 버전을 주입). 별도 노력 거의 없음.

### 2.5 L5 — 호환성 회귀 (Bug Museum)

**무엇을 잡나**
- 과거에 발견했던 결함이 다시 들어오는 것 (F1~F6 + 향후 발견 결함).
- 마이그레이션 중 silently 도입되는 의미 변경.

**비용**
- 케이스당 단위테스트 1개. 거의 0.
- 단, *"이 버그를 재현하는 가장 단순한 입력"* 을 정확히 캡쳐하는 노력이 핵심.

**ROI**
- **압도적으로 높음.** 본 모듈처럼 위임만 250개 있는 코드베이스에서는 결함 재발률이 매우 높다 (휴먼 카피 결함, IDE auto-complete 미스 등). Bug Museum 이 표준이어야 한다.

## 3. Q3 — source-set 별 테스트 분리

### 3.1 권장 토폴로지

50.architecture.md 의 권장 옵션(multi-module)을 따른다고 가정. 테스트도 동일 구조로 분리.

```
.
├── common/
│   ├── src/main/java/                  ← 공용 컨버터
│   └── src/test/java/                  ← 공용 컨버터 단위 테스트
├── servlet5/
│   ├── src/main/java/                  ← 5.0 production
│   └── src/test/java/                  ← 5.0 unit + contract + integration
├── servlet6/
│   ├── src/main/java/                  ← 6.0 production
│   └── src/test/java/                  ← 6.0 unit + contract + integration
└── servlet61/
    ├── src/main/java/                  ← 6.1 production
    └── src/test/java/                  ← 6.1 unit + contract + integration
```

(만일 multi source-set 방식을 택할 경우 `src/jakarta6Test/java/` 등으로 분기.)

### 3.2 Gradle source-set 설정 예시 (multi-module 기준)

각 서브프로젝트 build.gradle 의 dependencies + test task 는 50.architecture.md §5.4~5.6 참조. 통합 테스트의 의존성은 다음과 같이 분리한다:

```groovy
// servlet6/build.gradle 에 통합 테스트 의존성 추가
dependencies {
    testImplementation 'org.apache.tomcat.embed:tomcat-embed-core:10.1.30'
    testImplementation 'org.awaitility:awaitility:4.2.1'
}

test {
    useJUnitPlatform()
    // 단위·contract 테스트만 기본 실행, 통합 테스트는 @Tag 로 분리
    useJUnitPlatform { excludeTags 'integration' }
}

task integrationTest(type: Test) {
    description = '통합 테스트 (Tomcat embed)'
    group = 'verification'
    useJUnitPlatform { includeTags 'integration' }
}

check.dependsOn integrationTest
```

### 3.3 공통 테스트 추출 가능성

`adapter.servletElementConverter.EnumsConverter` 등 common 모듈에 들어간 컨버터는 common 모듈의 `src/test/java` 에서 한 번만 테스트한다. 단 양쪽 API 인터페이스가 5/6/6.1 동일하다는 가정 하에서.

각 버전 모듈은 자체 contract / 통합 테스트만 갖는다. 단위 테스트가 사본되긴 하나 fixture builder 와 contract reflection 헬퍼를 common 의 test-fixtures 로 분리하면 중복 최소화 가능:

```groovy
// common/build.gradle
plugins {
    id 'java-test-fixtures'
}
dependencies {
    testFixturesApi 'org.junit.jupiter:junit-jupiter-api:5.10.2'
    testFixturesApi 'org.mockito:mockito-core:5.6.0'
}

// servlet5/servlet6/servlet61 의 build.gradle
dependencies {
    testImplementation testFixtures(project(':common'))
}
```

→ `MockHttpServletRequestBuilder`, `DelegationContractTestSupport` 같은 test fixture 를 common 의 `src/testFixtures/java` 에 두면 세 모듈 모두 import 가능.

### 3.4 통합 테스트는 어디에?

세 가지 옵션:

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 각 모듈의 `src/test/java` 안에 `@Tag("integration")` 으로 분리 | 단일 jar 빌드와 동일 컨텍스트. classpath 분리 자연스러움. | 단위/통합이 섞이면 빠른 피드백 손실. tag 분리 필수 |
| B. 별도 서브프로젝트 `:integration-tests` (네 번째 모듈) | 통합 테스트의 의존성·실행 환경을 어댑터 빌드와 격리. CI 에서 통합만 따로 실행 가능 | 빌드 토폴로지 복잡도 증가 |
| C. 단일 `src/integrationTest/java` source-set + cross-version param | 단순. JUnit `@ParameterizedTest` 가 컨테이너 부트를 매개변수화 | 1개 JVM 으로 5/6/6.1 컨테이너 jar 를 동시에 클래스패스에 올려야 함 — 가능하지만 classpath isolation 필요 |

→ **권장: 옵션 A 를 기본**, `@Tag("integration")` 으로 분리 → CI 에서 별도 task. 모듈마다 컨테이너 버전이 자연스럽게 정해지므로 cross-version 격리도 자동.

## 4. Q4 — Mock 전략

### 4.1 Mockito 5.x 사용 시 6.0 인터페이스 지원

| 인터페이스 | Mock 가능성 | 주의점 |
|---|---|---|
| `javax.servlet.*` 4.0 | OK | 기존 그대로 |
| `jakarta.servlet.*` 5.0 | OK | 현 코드 |
| `jakarta.servlet.*` 6.0 | OK. 단 `ServletRequest.getServletConnection()` 같은 신규 추상 메서드는 `RETURNS_DEFAULTS` 로 `null`/0 반환. Mockito 가 자동 default. | `getRequestId()` 등이 항상 `null` 반환 → 어댑터가 null-safe 인지 검증 |
| `jakarta.servlet.*` 6.1 | OK. default 메서드(`sendRedirect(loc,sc)`)는 Mockito 가 기본적으로 *spy 가 아닌 한* default 구현을 호출하지 않음. `Answers.CALLS_REAL_METHODS` 또는 `MockSettings.defaultAnswer` 명시. | 6.1 default 메서드 위임 검증 시 `mock(HttpServletResponse.class, withSettings().defaultAnswer(CALLS_REAL_METHODS))` |

### 4.2 양쪽 동시 mocking — "어댑터 안에서 원본을 다시 변환" 시나리오

예: javax → jakarta 어댑터의 `getSession()` 이 javax `HttpSession` 을 반환받아 jakarta 래퍼로 감싸 반환. 검증 흐름:

```
1. mockJavaxRequest = mock(javax.servlet.http.HttpServletRequest.class)
2. mockJavaxSession = mock(javax.servlet.http.HttpSession.class)
3. when(mockJavaxRequest.getSession()).thenReturn(mockJavaxSession)
4. when(mockJavaxSession.getId()).thenReturn("S-1")

5. jakartaReq = ServletAdapter.adaptToJakarta(mockJavaxRequest)
6. jakartaSession = jakartaReq.getSession()                  // 어댑터가 javax→jakarta 래퍼 생성
7. assertEquals("S-1", jakartaSession.getId())                // 위임 확인
8. verify(mockJavaxRequest).getSession()
9. verify(mockJavaxSession).getId()
```

→ Mockito mock 은 양쪽이 동시에 mocking 되어도 충돌하지 않는다 (다른 인터페이스). 단, 어댑터가 *중간에 컨버터를 거치는* 경우 (예: `AsyncContextConverter`), mock 의 invocation 카운트를 통해 그래프 위치를 검증해야 한다.

### 4.3 RETURNS_SMART_NULLS

```java
mock(HttpServletRequest.class, withSettings().defaultAnswer(RETURNS_SMART_NULLS))
```

미stub 메서드 호출 시 `SmartNull` 을 반환 → 이후 사용 시 stack trace 가 호출 지점을 표시. **위임 검증 테스트에서 stubbing 누락을 빠르게 잡는다.** 권장.

### 4.4 ArgumentCaptor

`addCookie(Cookie)` 같은 변환 위임 검증에 필수.

```java
ArgumentCaptor<javax.servlet.http.Cookie> captor =
    ArgumentCaptor.forClass(javax.servlet.http.Cookie.class);
verify(mockJavaxResponse).addCookie(captor.capture());
javax.servlet.http.Cookie passed = captor.getValue();
assertEquals("foo", passed.getName());
assertEquals("bar", passed.getValue());
```

### 4.5 mock 한계

- `final` 클래스/메서드 mocking 은 `mockito-inline` 필요. 본 프로젝트는 모두 인터페이스 기반이라 무관.
- Lambda/익명 클래스 (예: `AsyncContextConverter` 의 익명 `AsyncContext`) 는 mock 할 수 없음 — 직접 instantiate 후 위임 검증.
- 정적 메서드 (없음) / 생성자 (없음) — 무관.

## 5. Q5 — Contract / Property-based Testing

### 5.1 아이디어

어댑터의 본질적 계약:

> 어댑터 `A` 가 인터페이스 `I` 를 implements 할 때, `I` 의 모든 추상 메서드 `m` 에 대해, `m(args)` 를 호출하면 원본 `O` 의 동명·동시그니처 메서드 `O.m(args')` 가 호출되어야 한다 (단, `args'` 는 약속된 변환을 거친 인자).

이를 **reflection 으로 자동 검증**할 수 있다. 작성 비용은 한 클래스 ~150줄. 잡는 결함:

- 메서드 위임 누락 (인터페이스에 새 메서드 추가 후 어댑터가 빠뜨림).
- 호출 대상 오타 (F1: `read` → `readLine`).
- 인자 변형 누락.
- 자기 자신 호출 (F2 — 단, 변환 인자가 동일하면 위임 검증 통과할 수도 있어 별도 검증 필요).

### 5.2 의사 코드 — DelegationContractTest

```java
package com.snoworca.contract;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.MethodSource;
import org.mockito.ArgumentCaptor;
import org.mockito.Mockito;

import java.lang.reflect.*;
import java.util.*;
import java.util.stream.Stream;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

public class DelegationContractTest {

    /** 검증 대상 어댑터 클래스 + 그 어댑터가 위임받는 원본 인터페이스 + 어댑터가 구현하는 jakarta 인터페이스. */
    record AdapterSpec<O, J>(
        Class<O> originInterface,
        Class<J> jakartaInterface,
        java.util.function.Function<O, J> factory   // ServletAdapter::adaptToJakarta
    ) {}

    static Stream<AdapterSpec<?, ?>> specs() {
        return Stream.of(
            new AdapterSpec<>(
                javax.servlet.http.HttpServletRequest.class,
                jakarta.servlet.http.HttpServletRequest.class,
                ServletAdapter::adaptToJakarta),
            new AdapterSpec<>(
                javax.servlet.http.HttpServletResponse.class,
                jakarta.servlet.http.HttpServletResponse.class,
                ServletAdapter::adaptToJakarta),
            new AdapterSpec<>(
                javax.servlet.ServletContext.class,
                jakarta.servlet.ServletContext.class,
                ServletAdapter::adaptToJakarta)
            // ... 양방향 확장
        );
    }

    @ParameterizedTest
    @MethodSource("specs")
    @SuppressWarnings({"unchecked","rawtypes"})
    void everyJakartaMethodMustDelegateToOrigin(AdapterSpec spec) throws Exception {
        Object origin = mock(spec.originInterface(), RETURNS_SMART_NULLS);
        Object adapter = spec.factory().apply(origin);

        for (Method m : spec.jakartaInterface().getMethods()) {
            if (m.isDefault() || Modifier.isStatic(m.getModifiers())) continue;
            if (isBlacklisted(m)) continue;                  // 명시적 정책 메서드 (UnsupportedOp 등)
            Object[] args = sampleArgs(m.getParameterTypes());

            // 호출
            try {
                m.invoke(adapter, args);
            } catch (InvocationTargetException ignoredException) {
                /* 일부 메서드는 stub 부재로 NPE — 그래도 위임 자체는 일어남 */
            }

            // 원본 인터페이스에 같은 이름 + 같은 파라미터 종류의 메서드가 있다면 그게 호출됐어야 함
            Method originMethod = findCorrespondingOrigin(spec.originInterface(), m);
            if (originMethod != null) {
                // verify 가 throw 하면 위임 누락 / 잘못된 메서드 호출
                originMethod.invoke(verify(origin), sampleArgsForOrigin(originMethod.getParameterTypes(), args));
            }
        }

        verifyNoMoreInteractions(origin);   // 어댑터가 엉뚱한 메서드를 부른 경우 잡힘
    }

    private static Object[] sampleArgs(Class<?>[] types) {
        Object[] out = new Object[types.length];
        for (int i = 0; i < types.length; i++) {
            out[i] = sample(types[i]);
        }
        return out;
    }

    private static Object sample(Class<?> t) {
        if (t == String.class) return "_sample_";
        if (t == int.class || t == Integer.class) return 42;
        if (t == long.class || t == Long.class) return 42L;
        if (t == boolean.class || t == Boolean.class) return false;
        if (t.isArray()) return Array.newInstance(t.getComponentType(), 0);
        if (t.isInterface()) return mock(t, RETURNS_SMART_NULLS);
        // ... 더 풍부한 sampler 가능
        return null;
    }

    /** 어댑터 정책상 의미적 변경이 있는 메서드는 일반 contract 에서 제외 (예: setStatus(int,String) 폴백 시) */
    private static boolean isBlacklisted(Method m) {
        return Set.of("hashCode", "equals", "toString", "wait", "notify", "notifyAll", "getClass")
                  .contains(m.getName());
    }
}
```

핵심 트릭:
1. **mock 으로 원본 생성** → 어댑터 생성 → **인터페이스의 모든 메서드를 reflection 으로 호출** → `verify(origin).동명메서드(...)` 가 통과해야 함.
2. `verifyNoMoreInteractions` 로 **잘못된 메서드를 호출했는지** 검출 (F1 의 `readLine` 같은 경우).
3. 인자 변환 정책이 있는 메서드는 별도 화이트리스트로 빼고 개별 테스트로 보완.

### 5.3 jqwik vs reflection 자체작성

| 방식 | 장점 | 단점 |
|---|---|---|
| **자체 reflection driver** | 의존성 0. 정확히 필요한 것만. 본 위임 패턴에 특화. | 일반 property-based 기능(자동 shrink, 풍부한 generator) 없음. |
| **jqwik (`net.jqwik:jqwik:1.8`)** | property 도메인이 넓으면 강력. shrink 가능. | 학습곡선 + 의존성 추가. 위임 검증은 jqwik 의 핵심 가치(임의 입력 생성 + shrink)와 결이 다름. |

→ **권장: reflection 자체작성으로 충분.** 1개 클래스 ~200줄. jqwik 은 도입 가치 낮음.

```java
package com.snoworca.integration;

import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServlet;
import org.apache.catalina.Context;
import org.apache.catalina.LifecycleException;
import org.apache.catalina.startup.Tomcat;
import org.junit.jupiter.api.*;

import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.net.URI;
import java.net.http.*;

public class JakartaHostedJavaxHandlerIT {

    private Tomcat tomcat;
    private int port;

    @BeforeEach void startTomcat() throws LifecycleException, IOException {
        tomcat = new Tomcat();
        tomcat.setBaseDir(java.nio.file.Files.createTempDirectory("tcat").toString());
        tomcat.setPort(0);                                        // 임의 포트
        tomcat.getConnector();

        Context ctx = tomcat.addContext("", null);

        // 1. 원본은 javax.servlet HttpServlet (레거시 코드 시뮬레이션)
        javax.servlet.http.HttpServlet legacy = new javax.servlet.http.HttpServlet() {
            @Override protected void doGet(HttpServletRequest req,
                                           HttpServletResponse resp) throws IOException {
                resp.setStatus(200);
                resp.setContentType("text/plain; charset=UTF-8");
                resp.getWriter().write("hello-from-javax-handler");
                resp.addCookie(new javax.servlet.http.Cookie("legacy", "v1"));
            }
        };

        // 2. ServletAdapter 로 jakarta HttpServlet 형태로 감쌈
        jakarta.servlet.Servlet jakartaWrapped =
            adapter.servletElementConverter.ServletConverter.convert(legacy);

        // 3. 컨테이너에 등록 (Tomcat 10 = jakarta)
        Tomcat.addServlet(ctx, "leg", (HttpServlet) jakartaWrapped);
        ctx.addServletMappingDecoded("/leg", "leg");

        tomcat.start();
        port = tomcat.getConnector().getLocalPort();
    }

    @AfterEach void stopTomcat() throws LifecycleException {
        tomcat.stop(); tomcat.destroy();
    }

    @Test void getReturnsExpectedBodyAndCookie() throws Exception {
        HttpClient http = HttpClient.newHttpClient();
        HttpResponse<String> resp = http.send(
            HttpRequest.newBuilder(URI.create("http://localhost:" + port + "/leg")).GET().build(),
            HttpResponse.BodyHandlers.ofString());

        Assertions.assertEquals(200, resp.statusCode());
        Assertions.assertEquals("hello-from-javax-handler", resp.body());
        Assertions.assertTrue(resp.headers().allValues("Set-Cookie").stream()
            .anyMatch(v -> v.startsWith("legacy=v1")));
    }
}
```

## 7. Q7 — 크로스 버전 호환성 테스트

### 7.1 Parameterized 매트릭스

같은 시나리오를 5/6/6.1 모듈에 사본으로 배치 + JUnit5 `@ParameterizedTest` 로 Tomcat 부트스트랩 함수를 매개변수화.

```java
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.MethodSource;
import java.util.function.Supplier;
import java.util.stream.Stream;

class CrossVersionRedirectIT {

    enum Variant {
        SERVLET_5(() -> new TomcatRunner("10.0.27", 8)),
        SERVLET_6(() -> new TomcatRunner("10.1.30", 11)),
        SERVLET_6_1(() -> new TomcatRunner("11.0.0", 17));

        final Supplier<TomcatRunner> factory;
        Variant(Supplier<TomcatRunner> f) { this.factory = f; }
    }

    static Stream<Variant> variants() {
        return Stream.of(Variant.values());
    }

    @ParameterizedTest @MethodSource("variants")
    void sendRedirectReturns302AndLocation(Variant v) throws Exception {
        try (TomcatRunner runner = v.factory.get()) {
            runner.deploy(/* redirect servlet using adapter */);
            HttpResponse<String> resp = runner.get("/r");
            Assertions.assertEquals(302, resp.statusCode());
            Assertions.assertEquals("/target", resp.headers().firstValue("Location").orElse(null));
        }
    }
}
```

**단점**: 1개 JVM 클래스패스에 Tomcat 10.0/10.1/11 을 동시에 올리는 것은 거의 불가능. → 빌드 매트릭스로 분리.

### 7.2 빌드 매트릭스 분리 권장

`@ParameterizedTest` 는 *동일 모듈 안에서 mockJakarta API 동작이 5/6/6.1 어떻게 다른지* 검증할 때만 유용 (mock 기반은 jar 가 1개 라도 OK). **Tomcat 임베드 통합 테스트는 모듈별로 분리 + CI 매트릭스에서 병렬 실행** 이 정답.

## 8. Q8 — 비대칭 메서드 폴백 정책 검증

### 8.1 jakarta 6.0 → javax 4.0 변환에서 사라진 메서드

`adapter.javax.servlet.http.HttpSession` (6.0 모듈 버전) 의 `getValue/putValue/getValueNames/removeValue/getSessionContext`.

| 정책 | 검증 |
|---|---|
| `UnsupportedOperationException` (strict 모드) | `assertThrows(UnsupportedOperationException.class, () -> javaxSession.getValue("k"))` |

| `ServletRequest.getServletConnection()` | `assertNotNull(jakartaReq.getServletConnection()); assertNotNull(jakartaReq.getServletConnection().getConnectionId());` |

## 10. Q10 — AsyncContext / Listener 테스트

### 10.1 Thread-safety 결함 클래스

본 어댑터의 `AsyncContextConverter` 는 익명 클래스 위주라 자체 mutable 상태가 거의 없음. 그러나 `HttpUpgradeHandler` 의 `ThreadLocal<Class<?>>` 는 **누수 가능성**.

### 14.3 Mutation Testing (PIT) 도입

```groovy
plugins {
    id 'info.solidsoft.pitest' version '1.15.0'
}

pitest {
    targetClasses = ['adapter.**', 'com.snoworca.**']
    mutators = ['STRONGER']
    mutationThreshold = 80
    coverageThreshold = 90
    junit5PluginVersion = '1.2.1'
    timestampedReports = false
}
```

**왜 어댑터에 PIT 가 결정적인가?** — 단순 위임 코드의 가장 흔한 결함은 *"올바른 메서드 호출 자체를 빠뜨림"* 이다. JaCoCo 의 라인 커버리지는 "메서드를 호출하기는 했다" 만 증명하지만 PIT 의 *Void Method Call* 뮤테이터는 "이 메서드 호출을 제거해도 테스트가 통과하는지" 를 묻는다. **위임이 실수로 빠진 결함을 PIT 만이 잡는다.**

ROI 매우 높음. 단 PIT 는 빌드 시간 +30~60초 — 매 PR 이 아니라 **nightly + release tag** 에서만 실행 권장.

### 14.4 위임 위주 코드의 mutation 분석 핵심 뮤테이터

| 뮤테이터 | 어떤 결함을 잡나 | 예 |
|---|---|---|
| `VOID_METHOD_CALLS` | 메서드 호출 자체 누락 | `httpResponse.setStatus(sc)` 가 빠져도 테스트가 통과하면 해당 위임에 verify 가 없다는 뜻 |
| `RETURN_VALS` | 반환값 변형 | `return true → return false` 가 통과하면 boolean 위임에 어설션 없음 |
| `CONDITIONALS_BOUNDARY` | `<` ↔ `<=` 경계 | 적용 적음 |
| `REMOVE_INCREMENTS` | 카운터 누락 | StreamConverter 의 `isFinished` 플래그 갱신 검증 |

## 17. Q17 — Fixture / Builder 전략

### 17.1 복잡한 fixture 의 문제

`HttpServletRequest` mock 1개에 stubbing 10~30개 (getMethod, getRequestURI, getHeaders, getCookies, ...). 테스트당 30줄의 `when().thenReturn()` 보일러플레이트.

### 17.2 Builder 패턴

```java
public class MockHttpServletRequestBuilder {
    private String method = "GET";
    private String uri = "/";
    private final Map<String, String> headers = new LinkedHashMap<>();
    private final List<javax.servlet.http.Cookie> cookies = new ArrayList<>();

    public MockHttpServletRequestBuilder method(String m) { this.method = m; return this; }
    public MockHttpServletRequestBuilder uri(String u) { this.uri = u; return this; }
    public MockHttpServletRequestBuilder header(String n, String v) { headers.put(n, v); return this; }
    public MockHttpServletRequestBuilder cookie(String n, String v) {
        cookies.add(new javax.servlet.http.Cookie(n, v)); return this;
    }

    public javax.servlet.http.HttpServletRequest build() {
        javax.servlet.http.HttpServletRequest m =
            mock(javax.servlet.http.HttpServletRequest.class, RETURNS_SMART_NULLS);
        when(m.getMethod()).thenReturn(method);
        when(m.getRequestURI()).thenReturn(uri);
        when(m.getHeader(anyString())).thenAnswer(inv -> headers.get((String) inv.getArgument(0)));
        when(m.getHeaderNames()).thenAnswer(inv -> Collections.enumeration(headers.keySet()));
        when(m.getCookies()).thenReturn(cookies.toArray(new javax.servlet.http.Cookie[0]));
        return m;
    }
}
```

## 22. 결론

본 어댑터의 테스트 전략은 다음 5가지 원칙으로 요약된다.

1. **결함 박물관 (Bug Museum) 이 모든 것의 기반이다.** 현재만으로도 6개의 회귀 케이스가 즉시 추출되며, 이들이 회귀 슈트의 출발점이다.
2. **Reflection 기반 contract 테스트 1개로 250개 위임을 자동 검증한다.** 6.0/6.1 으로 확장될 때 새 메서드 누락도 자동 검출.
3. **실제 컨테이너 통합 테스트 없이는 어댑터를 신뢰할 수 없다.** Tomcat embed 가 본 모듈의 sine qua non.
4. **multi-module 분리는 테스트도 같이 분리시킨다.** 빌드 매트릭스를 CI 가 병렬로 굴리도록 한다.
5. **PIT mutation testing 은 위임 위주 코드의 결함을 가장 잘 잡는 도구다.** Phase 5 에서 반드시 도입.

위 5원칙과 Phase 1~5 의 단계적 도입을 따르면, 본 모듈은 **5.0/6.0/6.1 어느 라인에서도 정확하고 회귀 방지가 보장되는 어댑터** 로 발전한다.
