## 2. 각 결정 상세

### D1. 5.0 Critical 결함 7건 일괄 수정

**범위 (60.conversion-strategy.md §6.12 참조):**

| ID | 위치 | 결함 |
|---|---|---|
| D1.1 | `adapter/servletElementConverter/StreamConverter.java:41, 93` | `read(byte[], int, int)` 가 `readLine` 호출 — 바이너리 데이터 손상 |
| D1.2 | `adapter/jakarta/servlet/http/Part.java:50-56` | `getSubmittedFileName()` 무한 재귀 → 항상 `getName()` 반환 |
| D1.3 | `adapter/jakarta/servlet/ServletResponse.java:81-83` | `setContentLengthLong(long)` → `setContentLength((int)arg0)` narrow 변환 |
| D1.4 | `adapter/jakarta/servlet/ServletContext.java:337-339` | `setResponseCharacterEncoding` 이 `setRequestCharacterEncoding` 호출 |
| D1.5 | `adapter/javax/servlet/ServletContext.java:362-364` | `setRequestCharacterEncoding` 이 `setResponseCharacterEncoding` 호출 (방향 반대 동일 결함) |
| D1.6 | `adapter/jakarta/servlet/ServletRequest.java:173-179` | `getContentLengthLong` fallback 이 int 결과 반환 (2GB 이상 잘림) |
| D1.7 | `adapter/jakarta/servlet/ServletRequest.java:124-127` | `getRealPath(String)` — jakarta 5.0 인터페이스에 부재 메서드를 implements 시도 |

**처리 정책:**
- 1.0 의 **`servlet5` 모듈**에서 한 번에 수정. 별도 0.x 패치 라인은 만들지 않음.
- 각 결함 = 1 Bug Museum 회귀 케이스 (70.md §12.1 BM01~BM06 + D1.7 추가).
- 회귀 케이스가 **현재 결함 있는 코드에서 실패하도록** 먼저 작성 → 수정 후 통과. (TDD-style)
- `servlet6` / `servlet61` 모듈은 `servlet5` 의 수정된 사본에서 시작.

**우선순위:** Phase 1 (테스트 슈트 구축 시작과 동시에).

### D2. 6.0 + 6.1 분리 유지

`55.module-split-decision.md` 의 분석 결과:

| 옵션 | 결정적 약점 |
|---|---|
| B. 통합 + jakarta 6.0 API | 6.1 환경에서 `sendRedirect(loc, sc, clearBuffer)` 호출 시 `AbstractMethodError` |
| C. 통합 + jakarta 6.1 API | Java 17 강제 → 6.0 사용자 (Java 11) 컷오프 |
| D. 통합 + 리플렉션 분기 | 복잡도 폭증, 어댑터 본질 위반 |
| **A. 분리** | 위 셋의 결정적 약점 없음, 정량 비용은 LOC 사본 3,300 / CI 셀 1개 추가 (실질 유지보수 diff ~10 라인) |

**확정 토폴로지** (50.architecture.md §1.4 그대로):

```
common/        ← jakarta 5.0 핀, Java 8
servlet5/      ← jakarta 5.0,    Java 8
servlet6/      ← jakarta 6.0,    Java 11
servlet61/     ← jakarta 6.1,    Java 17
bom/
```

50.architecture.md §10.4 항목은 본 결정으로 마감.

### D3. Cookie attribute API 정책 = D (no-op + WARN)

**적용 범위:** `jakarta.servlet.http.Cookie.setAttribute/getAttribute/getAttributes` (6.0+ 신규).

**방향별 동작:**

| 방향 | 동작 |
|---|---|
| javax → jakarta 6+ (어댑터가 javax 4 Cookie 를 wrap 해 jakarta 6 인터페이스 노출) | 사용자가 jakarta 6 API 로 `setAttribute("SameSite", "Lax")` 호출 시도. 어댑터는 **자체 Map 보관하지 않음**. set 은 no-op + WARN once. get 은 null/empty. |
| jakarta 6+ → javax 4 (어댑터가 jakarta 6 Cookie 를 wrap 해 javax 4 인터페이스 노출) | 사용자가 javax 4 API 만 호출 가능. attribute API 호출 경로 자체가 없으므로 폴백 불필요. 단 어댑터가 `addCookie` 호출 시 원본 jakarta Cookie 가 가진 attribute 는 원본에서 유지됨 (어댑터가 만든 javax Cookie 는 attribute 없음). |

**로깅:** `java.util.logging` 으로 logger 명 `com.snoworca.servletadapter`. once-per-method dedup (ConcurrentHashMap).

**문서화:** README + javadoc 에 SameSite 등 정보 손실 가능성 명시.

### D4. strict 모드 = lenient default + opt-in

**적용 범위:** 60.md §6.2.1 의 정책 코드 B/D/E/F 가 default 일 때.

**활성화 방법 (우선순위 순):**
1. 시스템 프로퍼티: `-Dcom.snoworca.adapter.strict=true`
2. ServletContext init-param: `com.snoworca.adapter.strict=true`
3. (default) 비활성

**활성 시 동작:** 모든 B/D/E/F 폴백 분기에서 `UnsupportedOperationException` throw.

**근거:** 라이브러리의 silent migration 은 운영 환경 결함 추적을 어렵게 하지만 default 로 strict 를 두면 0.x → 1.0 마이그레이션 시 기존 사용자 코드가 깨질 위험. **lenient default 가 호환성 우선**, strict 는 운영 환경에서 명시적 활성화.

### D6. PIT mutation testing = Phase 5 (nightly)

**도입 시점:** 70.md §19 의 Phase 5 (P1 priority).

**실행 빈도:**
- 매 PR: JaCoCo (95%/100%) 만 강제. PIT 실행 안 함.
- nightly cron: PIT 실행, score ≥ 80% 게이트.
- release tag 푸시 시: PIT 통과 의무.

**근거:** PIT 빌드 시간 +30~60초로 매 PR 비용 큼. 본 어댑터 위임 위주 코드 특성상 PIT 가 가장 효과적이므로 nightly 로 안전망 확보.

### D7. Tomcat embed 통합 테스트 = 수용

**의존 추가:**

| 모듈 | testImplementation |
|---|---|
| servlet5 | `org.apache.tomcat.embed:tomcat-embed-core:10.0.27` (Servlet 5.0) |
| servlet6 | `org.apache.tomcat.embed:tomcat-embed-core:10.1.30` (Servlet 6.0) |
| servlet61 | `org.apache.tomcat.embed:tomcat-embed-core:11.0.0` (Servlet 6.1) |
| (모든 모듈) | `org.awaitility:awaitility:4.2.1` (async 테스트) |

**격리:** 각 모듈의 `src/test/java` 에 자체 Tomcat 만 사용. cross-version classpath 충돌 회피 (70.md §3.4 옵션 A).

**테스트 태깅:**
- 단위/contract = 기본 `test` task
- 통합 = `@Tag("integration")` + 별도 `integrationTest` task
- 보안 = `@Tag("security")` + nightly/release 만

**CI 영향:** `build-matrix` job 후 `integration-tests` job 이 모듈별 병렬 실행 (70.md §13.1 yaml).

**javax-host 시나리오 (Tomcat 9 embed):** `servlet5` 모듈의 통합 테스트에 `org.apache.tomcat.embed:tomcat-embed-core:9.0.85` 도 추가 (javax 4 컨테이너 시뮬레이션용). 단 6.x 모듈에는 추가하지 않음 (classpath 충돌).

### D8. 0.x → 1.0 alias 정책 = 옵션 B (servlet5 모듈 내 deprecated alias)

**채택:** `servlet5` 모듈 jar 내부에 0.x 패키지명의 `@Deprecated(since="1.0.0", forRemoval=true)` alias 클래스를 포함한다. 별도 0.x 백포팅 트랙은 운영하지 않는다.

**적용 범위:**

| 0.x 패키지 (alias) | 1.0 실제 구현 (delegate target) |
|---|---|
| `adapter.jakarta.servlet.*` | `adapter.jakarta.servlet5.*` |
| `adapter.javax.servlet.*` | `adapter.javax.servlet5.*` |
| `adapter.servletElementConverter.*` | `adapter.servletElementConverter5.*` |

alias 는 `servlet5` 모듈에만 포함. `servlet6` / `servlet61` 모듈은 신규 사용자 전용 — alias 없음.

**alias 클래스 패턴 (위임 권장):**

```java
package adapter.jakarta.servlet.http;

@Deprecated(since = "1.0.0", forRemoval = true)
public class HttpServletRequest
        extends adapter.jakarta.servlet5.http.HttpServletRequest {
    public HttpServletRequest(javax.servlet.http.HttpServletRequest req) {
        super(req);
    }
}
```

**채택 근거:**

- **운영 단순화**: 단일 Maven Central 게시 트랙. 0.x 백포팅 부담 0
- **결함 fix 즉시 전파**: alias 가 1.0 실구현을 위임하므로 D1 결함 9건 fix 가 alias 사용자에게도 자동 적용 (별도 cherry-pick 0건)
- **IDE 워닝 직접 전달**: `@Deprecated` → 사용자 코드에 컴파일러 워닝 표시 → 자연스러운 마이그레이션 유도
- **버전 분기 위험 0**: 단일 codebase, 0.x 와 1.x diverge 가능성 없음
- **사용자 베이스 작음**: 0.0.1 alpha 수준 → alias 부담 자체가 작음

**제거 일정:** v2.0 (목표: 2027 Q1) 에서 alias 일괄 제거. README + CHANGELOG 에 일정 명시.

**의무 부대 조건:**

- 모든 alias 클래스에 `@Deprecated(since="1.0.0", forRemoval=true)` 일관 부착
- Javadoc 에 "Use `adapter.jakarta.servlet5.*` instead" 명시
- README 의 1.0 마이그레이션 가이드 + v2.0 alias 제거 일정 섹션
- alias 경로의 BM01~BM10 회귀 1~2건 샘플 테스트 (cosmetic 검증)
- servlet5 jar size diff (alias 포함/미포함) 를 CHANGELOG 에 기록

**상세 SRS:** `docs/spec/50.compatibility.srs.md` MIG-REL-001 참조.

## 5. 1.0 작업 착수 직전 체크리스트

```
□ D1 Bug Museum 7건 회귀 케이스 작성 (현재 결함 있는 5.0 코드에서 실패 확인)
□ D2 multi-module Gradle 토폴로지 (settings.gradle 정비 + 모듈 디렉토리 생성)
□ D1 결함 7건 수정 (회귀 케이스 통과 확인)
□ servlet6 / servlet61 모듈 사본 + 폴백 정책 적용 (D3/D4)
□ Tomcat embed 통합 테스트 도입 (D7), IT01~IT15 시나리오
□ JaCoCo + 커버리지 게이트 (D6 의 PIT 는 Phase 5)
□ CI 매트릭스 yaml 작성 (70.md §13.1 기준)
□ README + 마이그레이션 가이드 작성
□ 1.0.0 게시
```

본 체크리스트는 1.0 작업 plan 의 Phase 분할 기초가 된다. 자세한 작업 분할은 후속 SRS / 구현 계획 단계에서 진행한다.
