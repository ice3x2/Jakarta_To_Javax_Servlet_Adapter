## 1. Scope Overview

본 문서는 `javax.servlet 4.0` ↔ `jakarta.servlet 5.0 / 6.0 / 6.1` 양방향 어댑터가 따라야 할 변환 의미론과 비대칭 시그니처에 대한 폴백 정책을 정의한다.

핵심 명세는 [docs/research/60.conversion-strategy.md §6.11](../research/60.conversion-strategy.md) 의 SPEC-1 ~ SPEC-16 을 SRS 형식으로 옮긴 것이다.

## 2. Scope Boundaries

### In Scope

- 인터페이스 완전 구현 (모든 추상 메서드)
- 위임 우선 원칙 (Decorator 패턴)
- 변환 합성 / 이중 wrap 회피 (`AdapterUnwrap` marker)
- 예외 변환 (`ServletException` 양방향)
- equals/hashCode 위임
- 비대칭 메서드 폴백 정책 (lenient default + strict opt-in)
- 폴백 가시성 (로깅 + diagnostics API)
- 컬렉션·스트림 변환 정확성
- `setContentLengthLong` long 정밀도 보존
- Cookie attribute API 손실 정책

### Out of Scope

- 0.0.1 결함 수정 자체 (→ `FIX`)
- 테스트 검증 방법 (→ `TEST`)
- 모듈 구조 (→ `MOD`)

## 3. Assumptions and Constraints

- 비대칭 메서드 매트릭스는 [60.conversion-strategy.md §6.1](../research/60.conversion-strategy.md) 에 정의된 약 30개 항목을 표준 입력으로 한다.
- 폴백 정책 코드 (A~G) 는 [60.conversion-strategy.md §6.2.1](../research/60.conversion-strategy.md) 의 정의를 따른다.
- 사용자가 strict 모드를 명시 활성화하지 않은 경우, 호환성 우선 lenient default 가 적용된다.

### FR-CONV-003 — 변환 합성 일관성 + 이중 wrap 회피 (SPEC-3 + SPEC-5)

| Field | Value |
|---|---|
| Type | functional |
| Target | v1.0.0 |
| Status | planned |
| Stability | evolving |
| Priority | high |
| Tags | identity, wrap, unwrap |
| Related Docs | [60.conversion-strategy.md §6.3, §6.11 SPEC-3,5](../research/60.conversion-strategy.md) |

#### Requirement

본 SRS 는 다음 marker 인터페이스를 신규 도입한다.

```java
package adapter.common;

public interface AdapterUnwrap<T> {
    T unwrap();
}
```

모든 어댑터 클래스는 `AdapterUnwrap<원본타입>` 를 implements 하며, `unwrap()` 은 위임 대상 원본 객체를 반환한다.

`ServletAdapter` 의 모든 `adaptToJavax / adaptToJakarta` 메서드는 호출 시점에 다음 사전 체크를 수행한다.

1. 인자가 `AdapterUnwrap` 인스턴스이면 `unwrap()` 으로 원본을 얻는다.
2. 원본이 반환할 namespace 의 타입이면 원본을 그대로 반환 (이중 wrap 회피).
3. 그렇지 않으면 새 어댑터 인스턴스로 wrap.

즉 `adaptToJavax(adaptToJakarta(javaxObj))` 는 `javaxObj` 와 `==` 동일성을 가진다 (원본 unwrap 가능 시).

#### Rationale

다중 wrap 은 호출당 두 번의 위임을 거치게 하여 성능 저하 + 객체 그래프 비대칭을 유발. marker 인터페이스로 자체 원본 노출.

#### Acceptance Criteria

- [ ] `AdapterUnwrap<T>` 인터페이스가 `common` 모듈에 존재한다.
- [ ] 모든 어댑터 클래스 (`adapter.jakarta.servletN.*`, `adapter.javax.servletN.*`) 가 `AdapterUnwrap<적절한_원본>` 를 implements 한다.
- [ ] `ServletAdapter.adaptToJavax(adaptToJakarta(javaxObj)) == javaxObj` 가 unit test 로 검증된다.
- [ ] 사용자가 어댑터 객체에 대해 `instanceof AdapterUnwrap` 확인 후 `unwrap()` 호출이 가능하다.

### FR-CONV-004 — equals / hashCode 위임 (SPEC-6)

| Field | Value |
|---|---|
| Type | functional |
| Target | v1.0.0 |
| Status | planned |
| Stability | evolving |
| Priority | high |
| Tags | equals, hashcode |
| Related Docs | [60.conversion-strategy.md §6.4](../research/60.conversion-strategy.md) |

#### Requirement

모든 어댑터 클래스는 `equals(Object)` 와 `hashCode()` 를 다음과 같이 override 한다.

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o instanceof AdapterUnwrap) {
        Object oUnwrapped = ((AdapterUnwrap<?>) o).unwrap();
        return this.unwrap().equals(oUnwrapped);
    }
    return this.unwrap().equals(o);
}

@Override
public int hashCode() {
    return this.unwrap().hashCode();
}
```

#### Rationale

`request.getSession()` 을 두 번 호출하면 두 어댑터 인스턴스가 반환되지만 같은 원본을 wrap 하므로 `equals` 가 `true` 를 반환해야 한다. 캐싱(wrapper pool) 을 도입하지 않고도 사용자 코드 호환성 보장.

#### Acceptance Criteria

- [ ] 동일 원본 객체를 두 번 wrap 한 어댑터 인스턴스 `a`, `b` 가 `a.equals(b)` 와 `b.equals(a)` 모두 true 를 반환한다.
- [ ] `a.hashCode() == b.hashCode()` 가 성립한다.
- [ ] Reflective contract test 가 equals/hashCode 위임을 검증한다.

### FR-CONV-005 — 예외 변환 (SPEC-4)

| Field | Value |
|---|---|
| Type | functional |
| Target | v1.0.0 |
| Status | planned |
| Stability | evolving |
| Priority | high |
| Tags | exception, servlet-exception |
| Related Docs | [60.conversion-strategy.md §6.5](../research/60.conversion-strategy.md) |

#### Requirement

`javax.servlet.ServletException` 과 `jakarta.servlet.ServletException` 은 어댑터가 try/catch 로 양방향 변환한다. 원본 예외는 `cause` 로 chain 된다.

`IOException`, `IllegalStateException`, `UnsupportedOperationException` 등 `java.lang` / `java.io` 표준 예외는 그대로 propagate 한다.

#### Rationale

namespace-specific 예외 한 가지만 변환 필요. 표준 예외는 namespace 가 동일하므로 변환 불필요. stack trace 는 cause chain 으로 보존.

#### Acceptance Criteria

- [ ] 어댑터가 위임 호출에서 `javax.servlet.ServletException` 을 catch 하고 `jakarta.servlet.ServletException` 으로 throw 하며, `getCause()` 가 원본을 반환한다.
- [ ] 반대 방향도 동일하게 동작한다.
- [ ] `IOException` 등 표준 예외는 어댑터를 통해 그대로 propagate 된다 (cause chain 없이).

### FR-CONV-006 — 컬렉션 변환 (eager snapshot, SPEC-11)

| Field | Value |
|---|---|
| Type | functional |
| Target | v1.0.0 |
| Status | planned |
| Stability | evolving |
| Priority | medium |
| Tags | collection, snapshot |
| Related Docs | [60.conversion-strategy.md §6.6](../research/60.conversion-strategy.md) |

#### Requirement

`getCookies()`, `getParts()`, `getServletRegistrations()`, `getFilterRegistrations()` 등 배열·컬렉션 반환 메서드는 eager snapshot 으로 변환한다.

- 호출 시점의 원본 상태를 캡처해 새 컬렉션/배열을 반환한다.
- 반환된 컬렉션의 mutation 은 원본에 반영되지 않는다.
- 원본이 `null` 을 반환하면 어댑터도 `null` 을 반환한다 (NPE 발생 금지).

#### Rationale

spec 권장 동작 + 사용자 코드의 NPE 방어. 0.0.1 의 `getCookies()` 는 null check 없이 enumerate → NPE 가능 (D9 결함).

#### Acceptance Criteria

- [ ] `getCookies()` 의 원본이 null 을 반환하면 어댑터도 null 을 반환한다 (NPE 없음).
- [ ] 어댑터의 `getCookies()` 호출 시 매번 새 배열이 반환된다 (`==` 동일성 없음).
- [ ] 반환된 배열의 mutation 이 원본 배열에 반영되지 않는다.

### FR-CONV-007 — Stream 변환 정확성 (SPEC-12)

| Field | Value |
|---|---|
| Type | functional |
| Target | v1.0.0 |
| Status | planned |
| Stability | evolving |
| Priority | critical |
| Tags | stream, read, write |
| Related Docs | [60.conversion-strategy.md §6.7, §6.12 D1](../research/60.conversion-strategy.md) |

#### Requirement

`ServletInputStream` / `ServletOutputStream` 어댑터의 모든 메서드는 원본의 **동일 시그니처** 메서드로 위임한다. 의미가 다른 메서드 (예: `read` → `readLine`) 로의 redirect 는 금지한다.

- `read()`, `read(byte[])`, `read(byte[], int, int)` 는 모두 원본의 동명 메서드로 위임.
- `readLine(byte[], int, int)` 는 별도 메서드로 유지.
- `isFinished()`, `isReady()`, `setReadListener()` 는 원본 동명 메서드 단순 위임.

#### Rationale

`ServletInputStream.readLine` 은 line terminator 까지만 읽는 의미. `read` 의 임의 바이트 읽기와 다름. 잘못 redirect 시 바이너리 데이터 손상.

#### Acceptance Criteria

- [ ] `read()` 호출 시 원본의 `read()` 가 호출된다 (mock verify, no `readLine` 호출).
- [ ] `read(byte[])` 호출 시 원본의 `read(byte[])` 가 호출된다 (no `readLine` 호출).
- [ ] `read(byte[], int, int)` 호출 시 원본의 `read(byte[], int, int)` 가 호출된다 (no `readLine` 호출). FR-FIX-001 회귀.
- [ ] `readLine(byte[], int, int)` 호출 시 원본의 `readLine(byte[], int, int)` 가 호출된다 (별도 시그니처 유지).
- [ ] `isFinished()` 호출 시 원본의 `isFinished()` 가 호출된다.

### FR-CONV-008 — setContentLengthLong long 정밀도 보존 (SPEC-13)

#### Requirement

`long` 인자를 받는 `setContentLengthLong(long len)` 어댑터 메서드는 다음을 따른다.

- 원본 인터페이스에 `setContentLengthLong(long)` 가 있으면 그대로 위임한다.

#### Acceptance Criteria

### FR-CONV-011 — strict 모드 (SPEC-9, opt-in)

| Field | Value |
|---|---|
| Type | functional |
| Target | v1.0.0 |
| Status | planned |
| Stability | evolving |
| Priority | high |
| Tags | strict-mode, opt-in |
| Related Docs | [60.conversion-strategy.md §6.11 SPEC-9](../research/60.conversion-strategy.md), [80.decisions.md D4](../research/80.decisions.md) |

#### Requirement

strict 모드는 사용자가 명시 활성화하지 않으면 비활성 (lenient default). 활성화 방법은 우선순위 순으로 다음 둘 중 하나.

1. 시스템 프로퍼티: `-Dcom.snoworca.adapter.strict=true`
2. ServletContext init-param: `com.snoworca.adapter.strict=true`

활성화 시 FR-CONV-010 의 모든 B / D / E / F 폴백 분기에서 `UnsupportedOperationException` 을 throw 한다. 단 SPEC-7 의 정책표에서 strict 정책이 "F (동일)" 인 다음 2개 메서드는 예외로 default 동작을 유지한다 (합성이 필수 — 추상 메서드 미구현 시 인터페이스 계약 자체가 깨짐):

- `ServletRequest.getRequestId()` — request attribute lazy UUID 캐싱 유지
- `ServletRequest.getServletConnection()` — 어댑터 내부 dummy `ServletConnection` 합성 유지

`ServletRequest.getProtocolRequestId()` 는 strict 정책이 "D (동일)" 이지만 `""` 반환이 spec 의 acceptable default 이므로 동일하게 default 유지.

`UnsupportedOperationException` 의 메시지는 다음 형식을 따른다.

```
"Strict mode: {ClassName}.{methodName}({args}) is unsupported in this direction.
 Reason: {removed in jakarta 6.0 | absent in javax 4.0}"
```

#### Rationale

lenient default 는 0.x → 1.0 마이그레이션 호환성 보장. strict 는 운영 환경에서 silent migration 방지를 위한 opt-in.

#### Acceptance Criteria

- [ ] 시스템 프로퍼티 `com.snoworca.adapter.strict=true` 설정 시 `HttpSession.getValue` 호출이 `UnsupportedOperationException` 을 throw 한다.

- [ ] 시스템 프로퍼티와 init-param 이 모두 설정 시 시스템 프로퍼티가 우선한다.

- 어댑터 자체는 새 mutable state 를 도입하지 않는 한 thread-safe 하다.
- `getRequestId()` 같은 자체 상태가 필요한 메서드는 request attribute 등 컨테이너 제공 thread-safe 보관소를 사용한다.
- diagnostics 카운터는 `ConcurrentHashMap` + `AtomicLong` 등 thread-safe 자료구조를 사용한다.
- 로그 dedup 도 `ConcurrentHashMap.putIfAbsent` 등 thread-safe 방식으로 구현한다.

`HttpUpgradeHandler` 의 ThreadLocal 패턴은 단일 스레드 동기 호출 가정 (현 코드 유지). 향후 안전한 factory 패턴으로 대체 검토.
